# ADR-0016: عقد الـ API لقطات ذهبية يتشاركها المستودعان

- **الحالة:** مُقرّ
- **التاريخ:** 2026-10-28
- **صاحب القرار:** صاحب المشروع (البند 8 من خطة الأساس الهندسي)

## السياق
الباكاند والواجهة في مستودعين منفصلين، وأنواع الواجهة مكتوبة يدوياً وأسماء الصلاحيات منسوخة يدوياً. إعادة تسمية حقل أو مسار أو صلاحية في أحد الطرفين تظهر عند المستخدم فقط: حقل فارغ، 404، أو زر لا يظهر لأحد بصمت.

## القرار
- مستودع الباكاند **يملك** العقد: لقطتان ذهبيتان `contract/permissions.json` و`contract/openapi.json` يولّدهما التطبيق الحقيقي، ويفشل CI عند أي اختلاف حتى يراجعه إنسان (نمط مصفوفة الصلاحيات).
- الواجهة تحتفظ بنسخة وتولّد منها أنواع DTO (مولّد صغير داخلي لا حزمة `openapi-typescript`، لأنها تفرض TypeScript 5 والمشروع على 6)، وتفحص: الأنواع محدّثة، كل نداء ثابت له مسار وفعل في العقد، نماذجها اليدوية تطابق الـ DTO وقت الترجمة، وأسماء `AppPermission` تطابق الكتالوج في الاتجاهين.
- لم نستبدل نماذج الواجهة اليدوية بالمولَّدة دفعة واحدة: **نفحصها** مقابل المولَّدة ونستبدل تدريجياً حين يكون ذلك أبسط.
- Swagger يعمل بـ`SupportNonNullableReferenceTypes` ليكون `string?` مقابل `string` صادقاً في العقد.

## البدائل
- مستودع واحد أحادي (monorepo): يحل المشكلة جذرياً لكنه إعادة تنظيم كبيرة غير مطلوبة الآن.
- توليد عميل كامل من OpenAPI: يربط الواجهة بقالب المولّد ويصعّب خصوصيات مثل الرفع المجزّأ والتنزيل.

## النتائج
- تغيير API يحتاج تحديث لقطتين ومزامنة النسخة في الواجهة؛ الـ CI في المستودعين لا يرى أحدهما الآخر، فالمقارنة بين النسختين محلية (`npm run contract:check`).
- لا يغطي التعدادات الصحيحة (قيم المراحل والأنواع) ولا أجسام الطلبات بعد.
