# ADR-0001: معمارية نظيفة مع CQRS عبر MediatR

- **الحالة:** مُقرّ
- **التاريخ:** تأسيسي (قبل 2026-09)
- **صاحب القرار:** صاحب المشروع

## السياق
نظام داخلي متعدد الوحدات (إجازات، مهام، صيانة، أجهزة، مشاريع…) يكبر بسرعة ويعمله أكثر من شخص. نحتاج حدوداً واضحة بين قواعد العمل والبيانات والواجهة كي لا تتشابك الوحدات.

## القرار
أربع طبقات بالاعتماد الآتي: `API → Application, Infrastructure` و`Infrastructure → Application, Domain` و`Application → Domain`.
- **Domain:** الكيانات والتعدادات فقط.
- **Application:** الأوامر والاستعلامات والمعالجات والمحققات (MediatR وFluentValidation)، وواجهات الخدمات `IXxxService`، **دون الاعتماد على EF Core**.
- **Infrastructure:** `DataContext` والخدمات التي تنفّذ الواجهات والهجرات.
- **API:** متحكمات رقيقة لا تعرف إلا `IMediator`، وسياسات الصلاحيات، والوسائط.
- المعالج يعبّر عن الأخطاء برمي استثناءات معروفة يحوّلها `ExceptionMiddleware` إلى رموز HTTP.

## البدائل
- طبقتان (متحكم + خدمات): أبسط، لكنها تخلط القواعد بالوصول للبيانات وتصعّب الاختبار.
- مكتبة وسيط أخرى أو استدعاء المعالجات مباشرة: لا فائدة تُذكر مقابل خط الأنابيب الموحّد (التحقق) الذي تعطيه MediatR.

## النتائج
- قواعد العمل تُختبر دون قاعدة بيانات (خدمات بديلة).
- كل طلب يمرّ بـ`ValidationBehavior` تلقائياً.
- يُفرَض آلياً في `tests/Architecture.Tests/LayeringTests` (اتجاه الاعتماد، عدم استعمال EF في Application، معالج واحد لكل طلب) و`ApiContractTests` (المتحكمات رقيقة؛ استثناءان معلنان كدَين).
