## Vacation business rules (core domain) — reviewed & hardened 2026-09-27
- Status flow: `PendingManager (1)` → `PendingBranchManager (3)` → `Approved (4)`; any stage can → `Rejected (5)` (stores RejectedByUserId, reason, date).
  `PendingAdministrative` was removed entirely 2026-09-27 (enum member, translations, `GetPendingForAdministrativeAsync`, and the status conditions in `VacationService`'s day-count/overlap queries). Its old int value (`2`) is left unassigned/reserved in the enum comment — never reuse it.
  A `Cancelled (6)` status was added the same day: the vacation's owner can cancel it (soft — `Status = Cancelled`, record kept for audit) only while it's `PendingManager` or `PendingBranchManager`; blocked once `Approved`/`Rejected`/already `Cancelled`. Endpoint: `PUT api/Vacations/Cancel/{id}`, policy `CancelVacation`. `Cancelled` is intentionally excluded from `HasOverlappingVacationAsync` and the paid/unpaid day-count queries — cancelling frees up that period and doesn't count against the monthly quota.
- Approver checks (`ApproveVacationCommandHandler`, rules in `Features/Vacations/VacationAccess.cs`, 2026-10-03): stage 1 (`PendingManager`) needs `ApproveVacationFirst`, stage 2 (`PendingBranchManager`) needs `ApproveVacationFinal`, both limited to vacations of **the approver's branch**; whoever approved stage 1 (`FirstApprovedByUserId`) can't also give the final approval; `SuperAdmin` bypasses all. Self-approval is blocked for everyone except SuperAdmin. (The enum names `PendingManager`/`PendingBranchManager` are historical — they mean first/final stage.)
- Create (`CreateVacationCommandHandler`): **SuperAdmin and anyone without a department cannot submit vacations** (`InvalidOperationException`; UI hides the form). The vacation of someone who holds `ApproveVacationFirst` **skips stage 1** and starts at `PendingBranchManager`. End ≥ start, no overlap with pending/approved vacations, `VacDayCount` = working days (see below), Department/Branch copied from the user. **Returns `List<VacationResponseDto>`, not a single one** — see paid-day splitting below.
- **Working days & payment (phase 1, user decisions 2026-10-04 — replaced the 2026-09-27 split-at-creation rule):**
  - Duration = **working days**: Friday (`VacationCalendar.WeeklyHoliday`) and the dates in `PublicHolidays` don't count. `VacDayCount` = working days; a range that is all holidays is rejected. **No retroactive requests; today is allowed** (`StartVac >= DateTime.Today`, mirrored in the UI form).
  - One request = **one `Vacation` row** (Create still returns a one-item list for UI compatibility). **Payment is decided at final approval only**: pending requests reserve nothing; `ApproveVacationCommandHandler.AllocatePaymentAsync` re-counts working days with the current holidays and `VacationCalendar.Allocate` splits them into `VacationSegment` rows (one per month × paid/unpaid run, `Days` = working days). Max **2 paid days per month pooled across all IsPaid types**, counting **approved** segments only (`GetApprovedPaidDaysByMonthAsync`). Non-paid type → all unpaid. Sets `PaidDays`/`UnpaidDays`/`IsPaid` (= any paid day), `FinalApprovedByUserId`/`FinalApprovedAt`; stage 1 sets `FirstApprovedAt`.
  - Concurrency: final approval runs in `IVacationService.RunExclusiveForUserAsync` (transaction + `sp_getapplock` per employee) so two approvals can't spend the same monthly quota; `Vacation.RowVersion` makes a second decision on the same request fail with a friendly message (`UpdateAsync` maps `DbUpdateConcurrencyException` → `InvalidOperationException`).
  - Text: `VacationRules.PaymentAr` ("يُحدَّد الدفع عند الاعتماد" while pending) and `VacationRules.RequestNumber` (`VAC-{year}-{id:D5}`) — single source for DTO, dashboard rows and notifier.
  - Holidays: `api/PublicHolidays` (`GetAll?year`/`Create`/`Update`/`Delete`). **One record per holiday with `StartDate`/`EndDate`** (user decision 2026-10-13: a 4-day Eid is one entry, edited and deleted whole). Holidays may not overlap (`FindOverlapAsync`); vacation calculations read the holiday days inside the period (`GetDatesAsync` expands the ranges). Migration `Holiday_Periods_ToDo_Item_Color` merged consecutive days with the same name into one record (a missing day splits them into two); its `Down` splits them back into one row per day. The table shows the period, the days and how many fall on a Friday. Permissions `ViewHolidays`/`CreateHoliday`/`EditHoliday`/`DeleteHoliday`; UI `/vacations/holidays`. `GET api/Vacations/PreviewDays?start&end` (policy `CreateVacation`) feeds the form's working-days preview.
  - Migration `Vacation_Working_Days_And_Payment_At_Approval`: pending rows get `IsPaid = 0` and `VacDayCount` re-counted without Fridays; legacy approved rows keep their old paid flag/calendar days and get month segments at startup (`DbSeeder.BackfillVacationSegmentsAsync`, only rows with no segments and no `FinalApprovedAt`).
- **Printing — the institution's paper "طلب إجازة" form (phases 2–3, 2026-10-04, from a photo of the real form):** `GET api/Vacations/Print/{id}` (policy `PrintVacation`, boundary = `VacationAccess.CanView`) → `VacationPrintDto` (`Features/Vacations/Queries/Print`): Hijri submission date (Um al-Qura + `VacationRules.HijriDayOffset` = +1, matched to the paper sample) + Gregorian, employee name / `PersonalIdNumber` (الرقم الذاتي) / `PhoneNumber` (int → leading 0 restored) / department, all vacation types as tick boxes, reason, and "رأي رئيس الفرع" = the final-stage decision with the deciding user's name + uploaded signature (`UserSignature`). `Vacation.RejectedAtStage` records which stage rejected (migration `Vacation_Print` backfilled it from `ManagerAccept` and granted `PrintVacation` to every role holding a vacation view/approve permission). UI: `features/vacations/vacation-print-page.ts` at `/vacations/print/:id` (outside the layout, A4, fixed paper colors, stamp placeholder), header: country names in `PRINT_HEADER` (`core/constants/print.ts`, shared with the report print), then the **request's branch name** (`Vacation.BranchId`, copied from the employee at submission — also used in «رئيس {الفرع}» and «أرشيف {الفرع}»). A per-branch "ترويسة المطبوعات" field was built and then **rejected by the user** (migrations `Branch_Print_Header` + `Remove_Branch_Print_Header`) — don't re-add it; the title «( طلب إجازة )» sits centred under the emblem with the number/date box on the right (the sheet overrides the global `table { min-width: 700px }`); "طباعة" buttons on the «إجازاتي» history and the review page. `User.PersonalIdNumber` (الرقم الذاتي) is text since migration `User_PersonalIdNumber_Text` (2026-10-04): optional, `nvarchar(20)`, latin letters/digits/dash, normalized by `UserRules.NormalizePersonalIdNumber` (trim + upper-case), **unique filtered index** (`IS NOT NULL`) + a friendly duplicate check in the create/update user handlers; the migration turned the old int zeros into NULL. Entered on the users page (create + edit). `User.PhoneNumber` (رقم التواصل) became text too (migration `User_PhoneNumber_Text`: 0 → NULL, 9-digit values get their leading 0 back): optional, validated as a Syrian phone by `Application/Common/PhoneRules` (shared with the maintenance client phone; mirrored in UI `core/utils/phone.ts`), stored without spaces. Both fields are on the users page (create + edit forms, shown under the name in the table, plus a "تاريخ الإضافة" column) and on the profile page (with a note when missing, since the vacation print needs them).
- **Approval context «سجل الموظف» (2026-10-04, user picked items 1/2/3/4/6, collapsed, colleague names shown):** `GET api/Vacations/ApprovalContext/{id}` (policy `AnyVacationApprove`; record check = `VacationAccess.EnsureCanDecide`, the same single rule the approve handler now uses) → `VacationApprovalContextDto`: last approved vacation already started + days since, current-month approved count/working days (from segments), payment projection if approved now (`VacationCalendar.Allocate` with approved-only usage + per-month quota), department colleagues with approved/pending vacations overlapping the request (names, of N active users), the employee's other pending requests. UI `features/vacations/vacation-context-panel.ts`, collapsed in each pending card on the review page, loaded on first open. No new permission, no DB change.
- **Attachments (2026-10-05, user decisions):** PDF or JPG/PNG only, ≤ 3 files × 5 MB, **at submission only** (no adding later), no new permission. `VacationAttachment` (metadata, included with every vacation list) + `VacationAttachmentContent` (bytes, separate table so lists never load files), cascade with the vacation. `POST Vacations/Create` takes `attachments` form files (controller converts `IFormFile` → `UploadedFileDto`, request limit 20 MB); the type is detected from the file signature (`VacationAttachmentRules`, mirrored in UI `VACATION_ATTACHMENTS`), never from the extension/browser. `GET Vacations/Attachment/{id}[?download=true]` (policy `AnyVacationView`, record check `VacationAccess.CanView`). UI `features/vacations/vacation-attachments.ts` (chips → modal preview of image/PDF via blob URL, download) on the review cards/team table and the «إجازاتي» history; picker in the «تقديم طلب إجازة» window of «إجازاتي». Migration `Add_Vacation_Attachments` — its two `IX_MaintenanceRequests_DeliverySign*` index ops were removed by hand (the `Add_DeviceMaintenance` Designer was built without them, but `Maintenance_Delivery_Signature` already created them in the DB).
  - Not done yet: an activity log table, holiday/type settings like per-type caps.
- **«إجازاتي» page (2026-10-13, user decision — moved out of the profile):** `/vacations/my` (`features/vacations/pages/my-vacations-page.ts`) is the first link of the sidebar section «الإجازات». It is shown with `ViewVacations` or `CreateVacation` (`MY_VACATIONS_ACCESS`).
  - **Four cards** from the user's own vacations (`Vacations/My`, no backend change): paid days this month out of 2 (from approved segments, `VACATION_PAID_DAYS_PER_MONTH` mirrors `VacationRules.MaxPaidVacationDaysPerMonth`), approved working days this year, pending requests, and the current or next vacation.
  - **History** «سجل إجازاتي» with print, cancel (through `ConfirmService`) and attachments.
  - **«تقديم طلب إجازة»** (`CreateVacation`) opens `components/vacation-request-dialog.ts` in a modal: type, dates (`notInPast`), working-days preview, reason and attachments.
  - The profile page now shows only the personal data and the signature, plus an «إجازاتي» button. Employee vacation notifications open `/vacations/my` (review notices still open `/vacations/review`), and the vacation print's back link goes there too.


## Electronic signatures (2026-10-04, user decisions)
- `UserSignature` is a **versioned, append-only** table (Id, UserId, Image data-URL, CreatedAt, IsCurrent; filtered unique index = at most one current per user). It is **not** a column on `User` (big base64 image; many versions). Saving = retire the current row + insert a new current one (one transaction); "delete" = no current row. Old versions are never deleted because decisions reference them.
- **A signed decision stores the signature version current at that moment**, so reprinting never changes: `Vacation.FinalApprovedSignatureId` (final approval only — not the first approval) and `Vacation.RejectedSignatureId` (any rejection). Approving/rejecting **without** an uploaded signature is allowed → null → the print shows an empty signature box. The vacation print uses `IUserSignatureService.GetImageAsync(id)` of the decision, never the current one. Legacy decisions (before this) have no stored version → empty box.
- **Maintenance delivery sheet (same pattern, 2026-10-04):** a status whose `Stage` is `Delivered` is a "delivery" status (was the `IsDelivery` flag until migration `Maintenance_Status_Stages`, see "Maintenance stages" below). When a request **enters** a delivery status (edit form or `Status/{id}` — `StampDeliveryAsync` in `MaintenanceRequestCommands`), the request stores `DeliveredAt`, `DeliverySignerId` (oldest active holder of `SignMaintenanceReceipt` in the request's department) and `DeliverySignatureId` (that signer's current version, or null). A delivered request is closed, so it is never re-stamped. `Print/{id}` returns `delivered`/`deliveredAt` and, after delivery, the stamped signer + signature; before delivery only the expected signer's name with an empty box. Migration `Maintenance_Delivery_Signature` flagged "تم التسليم" and back-filled already-delivered requests with what the sheet used to print (current signer + current signature, `UpdatedAt` as the delivery date). `DeliverySignerId` is part of the user-delete guard (`ExistsForUserAsync`).
- New services that need a signature: add a `<Decision>SignatureId` FK (Restrict) on the decision record and set it from `GetCurrentIdAsync(userId)` in the handler — same pattern.
- **Signature pad UI (2026-10-05, user design request, rebuilt in Angular — not the React/shadcn original):** the profile panel (`features/profile/signature-panel.ts`) shows the current signature on a white «paper» card. «تغيير التوقيع» opens `signature-pad.ts` in a modal, with two tabs: «رسم» and «رفع صورة». The typed-name and saved-signatures tabs were declined (their fonts were Latin and loaded from a CDN). Ink is black or blue. The password is entered in the modal footer. `signature-ink.ts` builds each stroke as a filled outline whose width follows stylus pressure (or mouse speed) with tapered ends, exports a transparent PNG trimmed to the ink (max 1000×360, under the server's ~300KB limit), and `cleanUpload` turns paper white transparent and crops uploads. On a dark theme the ink is lifted on screen only; the saved image keeps the real colour. No backend change.
- Permission `ManageMySignature` guards `GET/PUT api/Auth/Signature` and the profile signature panel (was `SignMaintenanceReceipt`). **Changing or removing the signature requires the user's password** (`IPasswordHasher.Verify`; wrong password → `InvalidOperationException` = 400, never 401 which logs the UI out). Migration `Versioned_Signatures` made existing signatures the current version and granted `ManageMySignature` to roles holding `SignMaintenanceReceipt`/`ApproveVacationFirst`/`ApproveVacationFinal`. Nobody can read another user's raw signature except through a document they may print.
- Visibility (`VacationAccess`): `GetAll` = my own + my department's (`ViewDepartmentVacations`) or my branch's (`ViewBranchVacations`, or either approval permission); `GetById`/`User/{userId}` apply the same rule per record/user; `PendingForMe` = stage-1 vacations of my branch (`ApproveVacationFirst`) + stage-2 ones (`ApproveVacationFinal`, minus those I approved in stage 1), never my own.
- Notifications (`VacationNotifier`) go to permission holders in the vacation's branch (`IUserPermissionService.GetUsersWithPermissionAsync`): submit → First approvers (or Final ones if it skipped stage 1); first approval → employee + Final approvers; any rejection → employee (+ the first approver on a final decision); final approval → employee + first approver; cancel → First approvers before stage 1, first approver + Final approvers after.
- Endpoints (`api/Vacations`): `Create` (policy `CreateVacation`), `Cancel/{id}` (policy `CancelVacation`, owner-only), `My` (policy `ViewVacations`); `Approve/{id}` (PUT body `{approve, reason}`), `PendingForMe`, `Get/{id}`, `GetAll`, `User/{userId}` are plain `[Authorize]` with the checks above in the handlers.
