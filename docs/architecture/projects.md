## Projects & dossier — foundation (phase 0 of the «Janoubiyya» analysis, 2026-10-27, branch `north`, user-approved plan)
- Source: the PDF «تحليل النظام للجنوبية» (the engineering project life cycle: diwan → studies → contracts → project management with Gantt/delay/extension → handover/warranty, plus a pricing office). **Generic for every branch** (units, statuses and forms are data, not code per branch). Phases: **0 foundation** (project, versioned documents, audit log, task links, map provider, one report) → 1 schedule/delay/extension/field reports → 2 diwan/correspondence → 3 studies/technical offices → 4 contracts/committees/handover/warranty → 5 pricing office. A temporary-delegation step (rule 5 of the analysis, same unit only, re-checked at read time) comes after phase 0.
- **Project** (`Domain/Entities/Projects.cs`): belongs to one branch, handled by one department (changes with referral), optional shared `Site`, fixed `ProjectStage` (Study/Contracting/Execution/Handover/Warranty/Closed/Cancelled — never moves by date), optional official `ReferenceNumber` (unique per branch). Internal number `PRJ-{year}-{id:D5}` is computed (`ProjectRules.Number`). **Never deleted** — cancelled by stage (no `DeleteProject` permission). Money fields (study cost / contract value / budget) come with the phases that need them.
- **Visibility = fixed boundaries in `ProjectRules.Visible(viewer)`** (translatable to SQL; tested in `tests/Projects.Tests`): `ViewProjects` = I am a member or creator; `ViewDepartmentProjects` = handled by my department or has a member from it; `ViewBranchProjects` = my branch; organization-wide = all. `CreateProject`/`EditProject` imply seeing my own. **Referring a project to another department does not open it to that department's users** (rule 8): only members or holders of the department/branch permission see it. Documents, audit and the report follow the visibility of the project.
- **Documents**: `ProjectDocument` (title + fixed `ProjectDocumentKind` list) → `ProjectDocumentVersion` (number, SHA-256, size, source, uploader; content in the file store or `ProjectDocumentVersionContent`). A new upload **adds** a version, never replaces. Approving a version needs `ApproveProjectDocument` and **not the uploader**; an approved version is never edited or deleted; downloads of approved versions are audited. Max file size is up to **10 GB+** (user, 2026-10-27) → chunked, resumable upload (planned for step 0.3; file area `projects` must be added to `FileAreas` and the sweeper together), type detection from the head of the file, Range downloads; Database mode keeps a small cap, big files need `FileStorage:Mode = FileSystem`; Nginx/Kestrel limits and timeouts must be raised for the upload route.
- **Chunked upload (step 0.3a, built; user decisions 2026-10-27: server already on `FileStorage:Mode = FileSystem`, cap 50 GB default, 16 MB chunks, finalize in the background, Database mode ≤ 100 MB):** `api/ProjectUploads` (policy `UploadProjectDocument`, a session belongs to its starter only): `POST Start` → `PUT {id}/Chunk?offset=` (raw octet-stream, written straight to `<id>.part`, truncated at the offset first so a retry is safe; `ProjectUploadRules.DecideChunk` = write / already received / out of order / bad length) → `POST {id}/Complete` (202-style: status Processing) → poll `GET {id}` / `GET Mine` until Done or Failed; `DELETE {id}` cancels. State lives in `ProjectUpload` (Receiving/Processing/Done/Failed; document and version are created only when finalization succeeds, so abandoned uploads leave nothing; abandoned after 48 h and finished after 24 h are deleted by the worker). `API/Background/ProjectUploadWorker` (signal + 30 s poll, resumes Processing rows at startup, hourly cleanup) runs `ProjectUploadFinalizer`: SHA-256 over the file, type from content via `MapFileRules.Detect(Stream, name)` (now stream-based; same rules, forbidden files/macros/zips with executables refused), `IFileStore` area `projects` (`FileStore.Adopt` = rename on the same share) or bytes into `ProjectDocumentVersionContent` in Database mode, then `IProjectDocumentService.AddVersionAsync` = document + version number + audit entry + upload Done in one transaction (a unique-index collision on the version number retries). Settings `ProjectFileSettings` (`Projects:MaxFileGigabytes` 50, `MaxDatabaseFileMegabytes` 100, `ChunkMegabytes` 16 ≤ 32, `TempFolder`); part files in `<Root>/projects/_uploads` (FileSystem) so promotion is a rename. Nginx needs the chunk location (`deploy/linux/*nginx-ewms.conf`, `docs/DEPLOYMENT.md`); only one API instance may run (no claim step). A session longer than the 120-min JWT forces a re-login but resumes (the session-renewal backlog item fixes it at the root). Migration `Project_Document_Uploads`. Step 0.3b (document list/search, approval, Range download, delete) is next.
- **Documents API (step 0.3b, built)**: `api/ProjectDocuments` — `Search` (`ViewProjectDocuments`; filters projectId/kind/search (title, any file name, project name or `PRJ-…`)/from/to; newest upload first; only documents of visible projects), `Get/{id}` (all versions), `POST Approve/{versionId}` (`ApproveProjectDocument`; the uploader never approves his own version, not even SuperAdmin; refused in a closed or cancelled project; an atomic `UPDATE … WHERE NOT IsApproved` so two approvers cannot both succeed), `DELETE Delete/{id}` (`DeleteProjectDocument`; refused if any version is approved; versions deleted, files left to the sweeper), `GET Version/{versionId}/File?download=` (`DownloadProjectDocument`; **Range support**; image/PDF inline unless `download=true`, everything else attachment; `Cache-Control: private, no-store`; opening an **approved** version is audited once per open — the first request, without `Range` or starting at byte 0 — not per range request). Rules in `ProjectDocumentRules`; every handler loads the document with its project and members and calls `ProjectRules.EnsureView`. `IAuditLogService.WriteAsync` writes standalone entries. Step 0.4 (UI, built in the frontend repo on `north`): `features/projects` — see the UI `docs/ARCHITECTURE.md`.
- **Audit** (`AuditLog`, append-only, no update/delete anywhere): written **in the same transaction** as the operation (`AuditEntry` passed to the service that saves). General, but only the new modules write to it; the older logs (device inventory, maintenance activity, task activity) stay as they are. Read by `IAuditLogService` with `ViewProjectAudit`, limited to visible projects (entries with no project: organization-wide only).
- **API `api/Projects` (step 0.2)**: `Search` (paged; filters search/branch/department/site/stage; `AnyProjectView`), `Get/{id}`, `Create` (`CreateProject`; the creator becomes a member; the branch is the creator's, organization-wide users choose), `Update/{id}` (`EditProject`; full replace of department/site; `rowVersion`; stage change = audit action `stage`; closed/cancelled projects accept only a stage change that reopens them), `MemberCandidates/{id}`, `POST Members/{id}`, `DELETE Members/{id}/{userId}` (`EditProject`; members are active staff of the project's branch; notification `ProjectMemberAdded = 40` — 26–29 are reserved for attendance), `Audit/{id}` (`ViewProjectAudit`). Code: `Features/Projects/UseCases/` (one file per use case) + `ProjectContext`/`ProjectSupport`, audited saves in `ProjectService` (one transaction; a unique-index or concurrency failure becomes a friendly 400). Task links: `TaskLinkType.Project = 4` (resolver shows number + name only if the viewer sees the project). Map: `ProjectsMapLayerProvider` (key `projects`, unit «مشروع», filters department/stage, cancelled hidden unless chosen; every branch gets an automatic «المشاريع» layer — the UI must give provider layers without a colour a default). Report `projects` (group «المشاريع», permission `ExportProjectsReport`, boundary `ProjectRules.Visible`).
- 12 new permissions (`AppPermissions`, section «المشاريع»), any-of `AnyProjectView`; delete guards added for branch/department/site/user (`IProjectService.ExistsFor*`). Migration `Projects_Foundation` creates the tables only. Tests: `tests/Projects.Tests` (`dotnet test tests/Projects.Tests`).

## Projects — phase 1: schedule, delay, extension (2026-10-27, user-approved plan; steps 1.1 foundation, 1.2 schedule API, 1.3 delay/extension API and 1.4 UI (frontend repo, branch north) built; **phase 1B field reports was dropped on 2026-10-28**, see below)
- Scope of the phase: **1A** schedule/delay/extension (1.1 entities+rules, 1.2 schedule API, 1.3 delay+extension API, 1.4 UI with a hand-built SVG Gantt) **1B (daily/weekly field reports, quality reports) is NOT built and not planned: site engineers already use their own program (user decision 2026-10-28), so EWMS does not duplicate it — don't re-propose it; if the two ever need to meet, integrate with that program instead.** **User decisions:** day counting calendar by default with a per-extension «working days» option (no Friday/public holidays, via `VacationCalendar.IsWorkingDay`); **task weights are entered manually** (project % = weighted average of progress; planned % uses the same weights, optionally against the original baseline); extension to successors only after review (suggested, never automatic); dependency = finish→start only; critical flag set by hand (`ClassifyScheduleTask`); Gantt time runs right-to-left; schedule import from Excel is a later optional step.
- **Principle: the system warns and records, it never decides.** A task past its end is only an *overdue candidate* (`ScheduleRules.IsOverdueCandidate`); a delay is recorded by someone authorised; a justification or extension is approved by **someone other than who recorded/requested it**; original dates are fixed once at approval and never change; current dates change only by an approved extension; nothing extends or closes by date alone.
- Entities (`Domain/Entities/ProjectSchedule.cs`): `ProjectStartOrder` (one per project; completion/execution days, study cost only — contract values come with contracts), `ProjectSchedule` (versions: Draft/Approved/Superseded; one draft and one approved per project via the filtered unique index `IX_ProjectSchedules_OneDraftOneApproved`; creator ≠ approver; a revision copies tasks **with their original dates**), `ScheduleTask` (PlannedStart/End = current dates, Original* fixed at approval, manual `Weight` > 0, `IsCritical`, status/progress/actual dates; DB checks on dates, progress 0–100, weight > 0), `ScheduleDependency` (FK all Restrict — deleting a draft removes its dependencies first in the service; unique pair; no self), `ScheduleProgressEntry` (append-only history), `ScheduleDelay` (+ affected tasks; Unjustified/Justified; justified needs reason, approving authority, date and the approval **document version** — attaching alone never approves), `ScheduleExtension` (+ items with old/new dates and `MovesStart` for shifted successors, + supporting documents; Group = one number of days for all, Single = per task).
- Pure rules `Application/Features/Schedules/ScheduleRules.cs` (tested in `tests/Projects.Tests/ScheduleRulesTests.cs` + `ScheduleModelTests.cs`, 141 tests in all): date arithmetic, task/progress validation, weighted progress, overdue candidate, cycle detection and transitive successors, approval validation, `SnapshotOriginals`/`CloneForRevision`, extension line validation, `Preview` (never mutates), `SuggestedSuccessors`, `PreviewConflicts`, `StalePreviewProblem` (an extension prepared on old dates is refused after they changed), `ApplyExtension`, delay/justification rules.
- 10 new permissions (`ViewProjectSchedule`, `EditProjectStartOrder`, `EditProjectSchedule`, `ApproveProjectSchedule`, `UpdateScheduleProgress`, `ClassifyScheduleTask`, `RecordScheduleDelay`, `ApproveDelayJustification`, `RequestScheduleExtension`, `ApproveScheduleExtension`), any-of `AnyScheduleView`; their boundary is the project visibility (`ProjectRules.Visible`). Migration `Project_Schedule` creates the tables only.
- **Schedule API (step 1.2, built)**: `api/ProjectSchedules` — reads use `AnyScheduleView`: `Overview/{projectId}` (start order, versions, and for the approved one actual / planned / baseline % and overdue candidates), `Get/{id}` (tasks, dependencies, warnings, `canEdit/canApprove/canUpdateProgress/canClassify`), `Progress/{taskId}` (history). Writes: `PUT StartOrder/{projectId}` (`EditProjectStartOrder`; engineer and supervisor must be project members), `POST|DELETE Draft` (`EditProjectSchedule`; a draft is **empty, or a copy of the approved version carrying its original dates and dependencies**; one draft at a time; refused while an extension is Draft/Submitted), `POST Approve/{id}` (`ApproveProjectSchedule`; creator ≠ approver; the previous approved becomes Superseded first, then originals are snapshotted, in one transaction), `POST Tasks/{scheduleId}`, `PUT|DELETE Task/{id}`, `PUT Reorder/{scheduleId}`, `POST Dependencies/{scheduleId}`, `DELETE Dependency/{id}` (drafts only; a task with original dates cannot change its dates — only an approved extension does; assignee must be a project member), `PUT Progress/{taskId}` (`UpdateScheduleProgress`; **approved schedule only**; actual dates are completed from the status; lowering the % needs a note; every change appends a `ScheduleProgressEntry`; an unchanged repeat writes nothing), `PUT Classify/{taskId}` (`ClassifyScheduleTask`; draft or approved). Every write needs an open project (`ProjectRules.EnsureOpen`) and audits in the same transaction (`ScheduleService`). Warnings are shown, never blocking: no start order, tasks before the start date or after the completion days, dependency conflicts. Code: `Features/Schedules/UseCases/` + `ScheduleContext`/`ScheduleSupport`, `IScheduleService`/`ScheduleService`, DTOs `ProjectSchedule*Dtos.cs`. `ProjectService.ExistsForUserAsync` now also covers the schedule tables. A revision gives its tasks **new ids**: delays/extensions (1.3) stay attached to the version they were recorded on. Tests: `ScheduleHandlerTests` (162 in all).
- **Delay + extension API (step 1.3, built; same controller `api/ProjectSchedules`)**: a delay is **recorded by an authorised person** (`POST RecordDelay/{taskId}`, `RecordScheduleDelay`, approved schedule only) — passing the end date alone never creates one. Kind Unjustified (needs a note or action) or Justified; one *live* delay per task (any status but Resolved). The recorder alone submits the justification (`PUT Delay/{id}/Justify`: reason, approving authority, approval date, and a **document version of the same project**; attaching never approves), then **someone else** decides (`PUT Delay/{id}/Decide`, `ApproveDelayJustification`; rejection needs a reason; the recorder may re-justify after a rejection). Affected tasks are chosen by hand (same schedule); `Delay/{id}` returns **suggested** successors for review only. Extensions: `POST Extensions/{projectId}/Preview` (changes nothing), `POST Extensions/{projectId}` creates a Draft (`RequestScheduleExtension`; **one undecided request per project**; approved schedule only; Group = one number of days, Single = per task; calendar days or working days via `IPublicHolidayService`; `MovesStart` successors are chosen explicitly), `PUT|DELETE Extension/{id}` and `POST Extension/{id}/Submit` (requester only; submit refuses a request whose old dates no longer match), `PUT Extension/{id}/Decide` (`ApproveScheduleExtension`; not the requester; rejection needs a reason; approval re-checks staleness, applies the new **current** dates in one save, leaves the originals alone, and ends the live delays of the extended tasks). A linked delay must be Approved and on the current schedule. Detail DTOs carry dependency conflicts, suggested successors and `staleProblem`. Notifications (`ScheduleNotifier`, holders of the permission in the project's branch who can see it): types 41–45 (`ScheduleTaskOverdue`, `ScheduleJustificationSubmitted/Decided`, `ScheduleExtensionSubmitted/Decided`). **Overdue candidates**: `TaskReminderWorker` runs `ScheduleOverdueReminders` each cycle — approved-schedule tasks of open projects past their end and not completed/suspended notify the assignee and `RecordScheduleDelay` holders **once per end date** (`ScheduleTask.OverdueNotifiedFor`, migration `Schedule_Overdue_Notice`; an extension moves the end and re-arms it). Code: `Features/Schedules/UseCases/` (delay and extension use cases) + `ScheduleChangeContext`/`ScheduleChangeSupport`, `ScheduleNotifier.cs`, `IScheduleChangeService`/`ScheduleChangeService`. Tests: `ScheduleChangeHandlerTests` (183 in all).
