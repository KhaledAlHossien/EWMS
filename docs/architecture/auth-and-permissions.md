## Auth & permissions
- `POST api/Auth/login` → JWT with claims: NameIdentifier (UserId), Email, Name, Role, `DepartmentId`, `BranchId`.
- Tokens are stored in `UserTokens`; `OnTokenValidated` rejects revoked/expired tokens, so logout really revokes.
- **Login protection & password policy (2026-10-13, user decisions; migration `User_Login_Lockout`):**
  - `Application/Common/PasswordRules.cs` holds two classes:
    - `PasswordRules`: ≥ 8 characters, a letter and a digit, not the email or its local part. Applied on user create, admin password set, self-change, legacy register and the first admin. Existing hashes aren't checked. UI mirror: `core/utils/password.ts`.
    - `LoginRules`.
  - **Lockout:** 5 consecutive wrong passwords lock the account for 15 minutes (`User.FailedLoginCount`/`LockoutUntil`, UTC).
    - A correct password during the lock is still refused.
    - `AuthService.LoginAsync` returns a `LoginOutcome`; locked → **423** with the remaining minutes.
    - The owner gets a `LoginLocked` notification.
    - An unknown email and a wrong password share one message.
  - **Per-device limit:** rate-limiter policy `login` = 20 requests/minute per client IP (429 with an Arabic message), on `Auth/login` and `Auth/Password`. The IP comes from `UseForwardedHeaders`, so Nginx must send `X-Forwarded-For`.
  - **Unlock:** an admin setting a password (`UpdateUserCommandHandler`) clears the lock. `UserResponseDto.LockedUntil` (set only while locked) → «مقفل مؤقتاً» badge + a note in the edit dialog.
  - **Self-service change:** `PUT api/Auth/Password` `{currentPassword, newPassword}` (`Features/Users/Password/ChangeMyPasswordFeature.cs`).
    - Plain `[Authorize]`, an identity basic like `Auth/Me`.
    - A wrong current password = 400; the new one must differ. Then `RevokeSessionsAsync`.
    - UI `PasswordDialog` on the profile page clears the session; the login page shows «تم تغيير كلمة المرور…» (`?notice=password-changed`).
- **Security headers (2026-10-13):** `API/Middlewares/SecurityHeadersMiddleware`, first in the pipeline.
  - CSP:
    - `script-src 'self'`: no inline script. The theme bootstrap is UI `public/theme-init.js`; the production build has `inlineCritical: false` (its `onload` handler is an inline script).
    - `style-src 'self' 'unsafe-inline'` (Angular component styles).
    - `img-src data: blob:`; `frame-src`/`object-src blob:` (PDF preview in Chrome); `connect-src 'self'`; `frame-ancestors 'none'`.
  - Plus nosniff, `X-Frame-Options DENY`, `Referrer-Policy same-origin`, `Permissions-Policy` and COOP. HSTS only on HTTPS. No CSP on `/swagger`.
  - Nginx serving the UI files needs the same headers: `deploy/linux/ewms-security-headers.conf`, shipped in the API package under `deploy/`; keep its CSP identical.
  - Any new external resource, inline script or `fetch(data:…)` would be blocked. Verified with a Playwright run of the production build under this CSP: no violations.
- Current user (2026-10-10, review fix): **only the user id comes from the token.** `ICurrentUserService` has `UserId`, `IsAuthenticated` and `GetUserAsync()` = the user + role read from the DB (cached per request; a deleted/deactivated account → `UnauthorizedAccessException`). Its old `Role`/`BranchId`/`DepartmentId` claim readers were removed: a demoted SuperAdmin or a moved manager kept their old rights for up to the 120-minute session. Unit checks use `OrganizationRole.InBranch`/`InDepartment` (a user with no unit matches nothing — `null == null` must not pass) or `Viewer`. The JWT still carries `Role`/`DepartmentId`/`BranchId` claims, but the server never reads them. **Sessions are revoked** (`IUserService.RevokeSessionsAsync`) when `UpdateUserCommandHandler` changes a user's role, branch/department/office, deactivates them or sets a password — they must log in again.
- **Access model = Role-Permission only (user decision 2026-10-03, branch `Test_2`).** The user creates **one role per person** and grants it permissions; nothing is inferred from a role's name or from the user's placement (having an `OfficeId` does not make anyone "head of office"). A role is only a **permissions template** — it has no unit. The user's placement (branch / department / office) is set on the **user form** (final decision 2026-10-03, replacing the short-lived "unit on the role" design): all three are optional, `UserRules.EnsureUserReferencesAsync` derives the higher level from the lower (office → department → branch) and rejects conflicts; `SuperAdmin` has no unit. A placement or role change ends the user's open sessions (see "Current user" above).
  - **Every permission carries a fixed record boundary, coded in the handler and stated in its Arabic description** — never a configurable scope (the user explicitly rejected scopes). A different boundary = a new permission. Handlers read permissions via `Application/Common/Viewer` (`Viewer.CurrentAsync(IUserService, IUserPermissionService)`, `Has()`, `IsSuperAdmin`); `IUserPermissionService` (Infrastructure `UserPermissionService`) reads the role's permissions **from the DB by user id** (cached per request) and finds holders (`GetUsersWithPermissionAsync(permission, branch/department/office, exactUnit)`) for notifications. `PermissionAuthorizationHandler` and `DeviceAccessService` use it too, so role/permission changes apply immediately.
  - `OrganizationRole` now only has `IsSystemAdmin` (by role name `SuperAdmin`, which can't be renamed or deleted) plus `IsInDepartmentItself`/`IsInOffice` unit comparisons. Don't reintroduce position inference.
  - Boundaries: vacations — `ViewVacations` own, `ViewDepartmentVacations` my department, `ViewBranchVacations` my branch (+ stats page), `ApproveVacationFirst`/`ApproveVacationFinal` my branch (given to the branch's administrative staff, not necessarily department heads); dashboards — `ViewBranchDashboard` (branch + its departments/offices), `ViewDepartmentDashboard` (department + offices), `ViewOfficeDashboard`; task board — `AssignTaskToDepartment` (departments of my branch), `AssignTaskToOffice` (offices of my department), `AssignTaskToUser` (users of my office), `HandleUnitTasks` (tasks assigned to my own unit); maintenance — `ViewDepartmentMaintenance` (records of my department; edit/delete still need their own permission); work-task card view — assignee, or `ViewWorkTasks`/any dashboard permission in the same branch.
  - Migrations: `Add_Role_Organizational_Unit` (kept because it may already be applied on a dev DB) is undone by `Remove_Role_Organizational_Unit`, which first copies a role's unit to its users that have no placement. `Role_Permission_Only`: adds `Vacation.FirstApprovedByUserId` (the same person can't approve both stages; they get the final-decision notice), inserts the new permissions, splits `ApproveVacation` (legacy `Manager` → First, `BranchManager` → Final, others → both), grants the legacy-named roles exactly what their name used to imply, and deletes the `Module.*`/`ViewModuleAssignments`/`EditModuleAssignments`/`ViewAssignedTasks`/`CreateAssignedTask` rows left by the abandoned `test` branch.
  - Delete guard added: a user with vacations or vacation decisions cannot be deleted (`IVacationService.ExistsForUserAsync`) — deactivate instead. The `SuperAdmin` role cannot be renamed or deleted.
- Authorization = named policies (`[Authorize(Policy = "CreateUser")]`) checked by `API/Authorization/PermissionAuthorizationHandler` (see above). Endpoints whose permission is "any of several" (vacation view/approve, task board, dashboards) use plain `[Authorize]` and check in the handler. `GET api/Auth/Permissions` returns `{ permissions }` for the UI to refresh without re-login.
- Seeded roles: only `SuperAdmin` on a fresh DB (user decision on `Test_2`); every other role is created from the Roles page (which has "نسخ دور" to start from a similar role). Older DBs still have the legacy `BranchManager`/`Manager`/`OfficeManager`/`Emp` roles (they keep working; the migration `Role_Permission_Only` gave them the permissions their names used to imply). **First admin (2026-10-10, review fix):** no password in code — `DbSeeder` creates one only when no user has the SuperAdmin role, from `Seed:AdminEmail`/`Seed:AdminPassword` (env `Seed__…`, once; then remove the password). See `docs/DEPLOYMENT.md`.
- **Permissions are one per operation, everywhere** (user decision 2026-09-30; no `Manage…` permission exists any more). **Single source: `Application/Common/AppPermissions.cs`** (96 names + Arabic descriptions) — `DbSeeder` inserts missing ones, `AddAPIRigstrationServices` registers a same-named policy for each in a loop. Every policy used in a controller must be in that list; the reverse no longer holds — permissions that only set record boundaries (see the access model above) are checked in handlers.
  - Users `ViewUsers`/`CreateUser`/`EditUser`/`DeleteUser` (`Auth/register` = `CreateUser`); Branches `ViewBranches`/`CreateBranch`/`EditBranch`/`DeleteBranch`; Departments `ViewDepartments`/`CreateDepartment`/`EditDepartment`/`DeleteDepartment`; Offices `ViewOffices`/`CreateOffice`/`EditOffice`/`DeleteOffice`; Roles `ViewRoles` (incl. `Roles/Permissions`)/`CreateRole`/`EditRole`/`DeleteRole`; Vacations `ViewVacations`/`CreateVacation`/`CancelVacation`/`ApproveVacation` (approve + `PendingForMe`); Vacation types `ViewVacationTypes`/`CreateVacationType`/`EditVacationType`/`DeleteVacationType`; Work tasks `ViewWorkTasks`/`CreateWorkTask`/`EditWorkTask`/`DeleteWorkTask`; Device inventory `ViewDevices`/`CreateDevice`/`EditDevice`/`DeleteDevice` (one set for regions+sites+devices+installations); Maintenance — see its section.
  - **Every read has a View permission too, including form lookups** (user decision 2026-09-30, reversing the first version where they were open): `ViewDepartments` (`Department/Get|GetAll`), `ViewVacationTypes` (`VacationTypes/Get|GetAll`), `ViewMaintenanceLookups` (the 4 maintenance lookup controllers). So a role needs the lookup View permission next to the create/edit permission that uses it: vacation form → `ViewVacationTypes`; maintenance request form/search → `ViewMaintenanceLookups`; any branch/department picker (incl. the UI `getBranchLookup()`) → `ViewDepartments`. Migration `Add_View_Permissions_For_Lookups` granted them to the roles that relied on those reads at the time (`ViewDepartments` → every role, `ViewVacationTypes` → roles with vacation permissions, `ViewMaintenanceLookups` → roles with maintenance-request/lookup permissions). View permission names are plural (`ViewXs`).
  - **No permission policy on the controller (checked in handlers instead):** `AssignedTasks` (`AssignTaskTo*`/`HandleUnitTasks`), `Dashboard` (`View*Dashboard`, `ViewBranchVacations`/`ViewDepartmentVacations` for `Vacations`), vacation view/approve endpoints, `WorkTasks/My|View`; and truly open to any signed-in user: `Map` (SuperAdmin only inside), `Notifications`, `Auth/Me`, `Auth/Permissions`, `Devices/MyAccess`.
  - The permission only opens the operation; record-level scoping still lives in the handlers/rules (`UserRules`, `OfficeRules`, vacation handlers, `MaintenanceRules`, department delete = own branch).
  - Privilege-escalation guard: a non-SuperAdmin can't grant a role holding `CreateBranch`/`EditBranch`/`DeleteBranch` (`AppPermissions.IsBranchManagement`, used by role create/update, `UserRules`, `AuthService.RegisterAsync`).
- **Role grants:** SuperAdmin gets **every** permission on each startup (`DbSeeder`). The other seeded roles get defaults **only when the role row is first created** (fresh DB: vacation permissions + `ViewDepartments` + `ViewVacationTypes`) — after that the seeder never touches them, so the user's edits from the Roles page stick (user decision 2026-09-30: "I'll adjust the other roles myself"). Don't reintroduce per-startup grants for non-SuperAdmin roles.
- Renaming/removing a permission needs a migration (the seeder only adds): insert new rows, copy each role's grants old→new, delete the old rows (cascade). See `Split_Maintenance_Permissions` and `Split_All_Permissions` (the latter also dropped `ManageVacations`, which never guarded any endpoint, and the dead "Project" policies were removed from the API).
- UI (`F:\-EWMS-UI-main-main`, branch `yaman`) follows the same names: `core/constants/access.ts` mirrors `AppPermissions` (plus groups `APPROVE_VACATIONS`, `VACATION_STATS`, `TASK_OVERSIGHT`), `permissionGuard` accepts only `data.permission` / `data.anyPermission` (no role names), the home dashboard is picked by `View*Dashboard` permission, and the task board needs `ViewTaskBoard` (sidebar, route and the whole `AssignedTasks` controller; migration `Add_ViewTaskBoard_Permission` granted it to roles holding any assign/handle permission and to the legacy named roles) and shows a target-type selector when a role holds several `AssignTaskTo*`.

## Cross-cutting access rules (moved here from the maintenance notes, 2026-10-28)

- **Nothing is open to every signed-in user (user decision 2026-10-03).** Every controller endpoint carries a permission policy, except the identity basics `Auth/login`, `Auth/Me`, `Auth/Permissions`, `Auth/logout`, `Auth/Password` (and the UI's `/profile` page, where users land when they have no dashboard). New permissions for what used to be open: `ViewTaskBoard` (the whole `AssignedTasks` controller), `ViewNotifications` (`Notifications` controller **and** the SignalR hub; the UI starts the hub and shows the bell only with it), `ViewMyDashboard` (`Dashboard/Me`), `ViewOrganizationDashboard` (`Dashboard/Overview`, replacing the old by-name SuperAdmin check), `ViewMyWorkTasks` (`WorkTasks/My`), `SignMaintenanceReceipt` (`Auth/Signature`), `ViewBranchMap` (`Map/*`), `ViewDevices` (`Devices/MyAccess`). Endpoints that accept several permissions use **any-of policies** declared in `AppPermissions.AnyOf` (no DB rows; registered in `AddAPIRigstrationServices`; `PermissionRequirement` takes several names): `AnyDepartmentDashboard`, `AnyOfficeDashboard`, `AnyVacationView`, `AnyVacationApprove`, `AnyVacationStats`, `AnyMaintenanceAssign`, `AnyWorkTaskView`; the per-record boundary is still enforced in the handler. UI mirrors them in `core/constants/access.ts` (`DASHBOARD_ACCESS`, `WORK_TASK_VIEW`, …); `DashboardHome` shows the widest dashboard the permissions allow and redirects to `/profile` when none. Migrations `Add_ViewTaskBoard_Permission` and `Close_Open_Endpoints_Permissions` grant the new personal permissions only to the legacy named roles (and ViewTaskBoard to roles holding assign/handle permissions) — **custom roles must be granted them from the Roles page**.
- **Permissions are the only thing that controls what a person sees (user decision 2026-10-04).** No UI visibility depends on the role name, on the user's placement, or on data: `AuthService.isSuperAdmin` was deleted; the vacation request form/button need only `CreateVacation` (the server explains if the account has no department); the map appears on whatever home dashboard the user lands on for `ViewBranchMap` holders (including the organization overview); breadcrumbs start at the organization only with `ViewOrganizationDashboard`; the vacation-stats branch selector needs `ViewOrganizationDashboard`. Server side, `Viewer.IsOrganizationWide` (= `ViewOrganizationDashboard` or SuperAdmin) decides who may open any branch's dashboard, map and vacation stats. The one remaining by-name rule is `SuperAdmin` itself (unrestricted record access in handlers such as vacations, tasks and maintenance) — it holds every permission anyway.
- **Structure views are branch-bounded (2026-10-04, user report: a branch admin saw every department):** `ViewBranches`, `ViewDepartments`, `ViewOffices`, `ViewUsers` and `ViewWorkTasks` return only the viewer's own branch (and its departments/offices/users/tasks); the whole organization only for `Viewer.IsOrganizationWide` (`ViewOrganizationDashboard` or SuperAdmin). Single rule in `Application/Common/StructureScope` (`BranchOf`, `EnsureIncludes`), used by the GetAll/GetById handlers of branches, departments, offices, users (replacing the by-name SuperAdmin check) and work tasks. A user with no branch and no organization view sees nothing. Note the UI branch lookup (`getBranchLookup`) therefore shows only the own branch for such roles.
- **Roles page permission tree (UI):** fixed section titles at the top (`PERMISSION_SECTIONS` in `features/roles/roles-page.ts`: الإجازات / المهام / الصيانة / توثيق الأجهزة / لوحات المتابعة / الإدارة والهيكل, + "أخرى" for anything unlisted) → collapsible groups → permissions, with selected/total counts and select-all per section and per group. Add every new permission to a group there.

## Session renewal, secrets and the security scan (2026-10-28, engineering-foundation item 9)
- **Session renewal** (`Application/Common/SessionRules`, `AuthService.RenewAsync`, `POST api/Auth/Renew`, an identity basic): the token lives `JwtSettings:DurationInMinutes` (120); the UI renews an **active** user's session when ≤ 20 min are left (`core/utils/session-renewal.ts`: renews only if the user interacted in the last 20 min, so an idle user simply expires). The whole session is capped at `JwtSettings:MaxSessionHours` (default 12) from the login: past it, or for a revoked/expired token or a deactivated account, `Renew` answers 401 and the UI signs out. The renewal issues a **new** `UserToken` carrying the original `SessionStartedAt` (migration `Session_Renewal`) and shortens the old token to 2 minutes so in-flight requests don't fail. Every JWT now has a unique `jti`. Logout, password/role/placement changes and deactivation still revoke the user's tokens (the renewed ones too, since revocation is per user).
- **Secrets:** the tracked `API/appsettings.json` has **no secrets** (empty JWT key, empty device key, empty seed password, no connection-string password — `ConfigurationSecretsTests`). Development keys live in `appsettings.Development.json`, are published by definition, and their SHA-256 fingerprints (plus the old leaked ones) are in `API/SystemBuild/KnownPublicKeys.cs`: **outside Development the app refuses to start with any of them** (`StartupSettings.EnsureValid`; transitional escape hatch `Security:AllowKnownDevelopmentKeys=true`). Add the fingerprint of any key you ever commit.
- **Device key rotation:** `DeviceInventory:OldPasswordKeys` (array/`__0` env vars) keeps previous keys; `DevicePasswordProtector.Unprotect` tries the current key then the old ones (GCM authenticates which is right), and at startup `DbSeeder.EncryptDevicePasswordsAsync` re-encrypts everything saved under an old key and logs the count. Procedure: `docs/DEPLOYMENT.md`.
- **DataProtection** is configured explicitly (`SetApplicationName("EWMS")`, optional persistent `DataProtection:KeysPath`); nothing uses it today because sessions are JWT.
- **Security scan 2026-10-28 (results):** NuGet — no vulnerable packages (direct or transitive). Raw SQL — only parameterised `sp_getapplock` calls and one `FromSqlInterpolated` with a typed id. Anonymous endpoints — `Auth/login` only (enforced by `ApiContractTests`). File paths — storage keys are regex-validated before any path is built. UI — `bypassSecurityTrust*` is used only for blob URLs the app created and for the governorate stamp SVGs shipped with the app; no `eval`/`document.write`. **Open items:** (1) the JWT is kept in `localStorage` (readable by any script that runs in the page; the strict CSP is the mitigation — moving to an httpOnly cookie would also need CSRF protection and is a larger change); (2) `npm audit` reports 2 high advisories in `@angular/router` (SSR, unused) and `zod`, fixed by upgrading Angular to 22.2.x as a separate tested change; (3) no antivirus on uploaded files (documented in `docs/DEPLOYMENT.md`); (4) no automated dynamic scan (e.g. OWASP ZAP) yet — run one against a staging copy before the first public exposure.
