## Quality gates & tests (2026-10-27, engineering-foundation plan, user-approved)
- **CI** (`.github/workflows/ci.yml`, GitHub Actions; the repo is `KhaledAlHossien/EWMS`, «Require status checks» is on for `master`): restore, Release build with **warnings as errors** (`Directory.Build.props`: `TreatWarningsAsErrors`, `NuGetAuditMode=all` — a known-vulnerable package fails the build when online; `NU1900` stays muted offline), all tests, and `dotnet ef migrations has-pending-model-changes` (a model change without a migration fails). The UI repo has its own workflow (lint, cycles, `ng test`, production build with size budgets; `npm audit` is non-blocking until Angular is upgraded to 22.2.x — 2 known high advisories).
- **Unit tests** `tests/Projects.Tests` (pure rules + handlers with substitute services, 316 — the older modules' rules are in `Regression/`). **Integration tests** `tests/Integration.Tests` (46, ~55 s): the real app via `WebApplicationFactory<Program>` on a **SQL Server 2022 container** (Testcontainers; needs Docker running) — real migrations, seeding, middleware, policies, EF tracking. `ApiFixture` builds one container + a small organization (2 branches, preparer/approver/outsider users with their own roles) shared by the `api` collection; each test makes its own project through `ScheduleScenario`. **Why they exist:** unit tests with substitute services passed while the real app failed on an EF tracking conflict (assigning an untracked navigation to a tracked entity); the integration test `A_delay_is_recorded…` catches it (verified by re-introducing the bug).
- **Architecture tests** `tests/Architecture.Tests` (30, ~1 s, no DB/Docker): the design rules are enforced by reflection, so a violating change fails the build. `LayeringTests`: Domain depends on no other layer, Application only on Domain and **never on EF Core**, Infrastructure not on API, and every MediatR request has exactly one handler. `ApiContractTests`: every endpoint has a permission policy except the five identity basics (`Auth.Login` — the only anonymous one —, `ChangePassword`, `Logout`, `Me`, `Permissions`, `Renew`; the list is explicit and checked both ways), every policy used exists in `AppPermissions`, controllers only take `IMediator` (declared debt: `AuthController` takes `IAuthService`, `VacationsController` takes `IUserService` — move into handlers, then delete the entry), the permission catalog has unique PascalCase names, Arabic descriptions, valid any-of policies and matching constants. `ModelRulesTests` (EF model, no connection): cascade deletes only from the 34 known dependents (adding one = a conscious edit of `AllowedCascades`), no bool/enum default other than zero (the 2026-09-29 `HasDefaultValue(true)` bug), every `RowVersion` is a concurrency token, every entity has a key. The first run also found the maintenance-device permissions listed twice in `AppPermissions` (removed). **Adding an endpoint:** give it `[Authorize(Policy = "...")]` (or a class-level policy) — the test tells you if you forgot.
- **Permission matrix (2026-10-27), two layers with different jobs.** (1) *Intent* — `tests/Architecture.Tests/permission-matrix.txt` is a reviewed snapshot of every endpoint and its policies (`GET api/X → ViewTaskBoard + ExportTasksReport`); `PermissionMatrixTests` fails on any difference, so swapping/adding/removing a policy shows up in the commit diff and a human approves it. To accept a change: `UPDATE_PERMISSION_MATRIX=1 dotnet test tests/Architecture.Tests -c Release --filter matrix_matches` and commit the file. It also forbids a data-changing POST/PUT/DELETE behind a view-only permission (exceptions: `AssignedTasks`, `Notifications`, whose gate is «عرض» by design and whose record rules live in the handlers). (2) *Enforcement* — `Integration.Tests/AuthorizationMatrixTests` (own container, ~45 s) probes **every** endpoint generated from the controllers: no token → 401; role with no permissions → the policy denial; a role holding only what the endpoint needs → passes the gate (and never a 5xx with empty input); a role holding everything except it → denied. **A controller's policy and an action's policy both apply (all must pass)** — `Scan.ActionInfo.Policies` / the matrix show them as `A + B`. Policy denial = 403 with the fixed message «ليس لديك صلاحية لهذا الإجراء» (JSON-escaped); a handler's own 403 has a different message. Endpoints are called with ids that don't exist, so nothing real is touched. The matrix proves a policy is *enforced*; the snapshot proves it is the *intended* one.
- **Handler structure (2026-10-28, engineering-foundation item 5, no behaviour change):** one handler per use case. Layout for a feature: `UseCases/<Name>.cs` = request record + validator + handler (primary-constructor `public class XHandler(<Feature>Context ctx) : IRequestHandler<…>`); `<Feature>Context` (sealed, registered `AddScoped` in `AddApplicationRegistrationServices.cs`) = the services the handlers share plus the loading/guard code used by two or more use cases (`ViewerAsync`, `LoadProjectAsync`, `DetailAsync`…) — composition, not inheritance; `<Feature>Support` (static, consumed with `using static`) = pure shared helpers (DTO mapping, `Today`, `Format`); a helper used by one use case stays inside that handler; request-DTO validators shared by several commands sit in `<Feature>RequestValidators.cs`. Done for `Projects` (project, documents, uploads; `ProjectUploadFinalizer` is its own file) and `Schedules` (schedule, delay/extension). Unit tests call the handlers through `tests/Projects.Tests/HandlerFacade` (reflection: finds the handler of a request and builds it from the context), so test bodies don't name handlers. Rule enforced in `LayeringTests`: a new handler class may serve only one request; the 28 older multi-request handlers are a declared list (`LegacyMultiRequestHandlers`) — split a module's handler when you next change that module and delete its names from the list (the test fails on stale names). A new use case = a new file in `UseCases/`, nothing else to edit except a context/support member if it needs one.
- Cross-repo mirror (backend `AppPermissions` ⇄ UI `access.ts`) is not checked by either CI yet: plan item 8 (OpenAPI/contract check). The UI side checks `access.ts` ⇄ the roles-page tree (`features/roles/utils/permission-sections.spec.ts`).
- Run: `dotnet test EWMS.slnx -c Release` (**Release**, because the user's running `API.exe` locks `API\bin\Debug`). Integration project settings are in-memory (`ApiFixture`), nothing touches the dev `EWMS` database.
- **Regression tests for the older modules (2026-10-28, engineering-foundation item 6; risk first, every one verified by mutation — flipping the rule makes it fail).** Unit (`tests/Projects.Tests/Regression/`, `Application` exposes internals to `Projects.Tests`): `VacationCalendarTests` (Friday and public holidays, the pooled 2 paid days per month from approved segments only, month-boundary split, payment text, reserved status value 2), `VacationAccessTests` (stage permissions, branch limit, no self-approval except SuperAdmin, first≠final approver, view boundaries, `null == null` never matches), `AssignedTaskRulesTests` (the task-board state machine, review freeze, return note, who handles/assigns/sees), `SecurityRulesTests` (password policy, lockout constants/message, device-password AES-GCM: round trip, fresh nonce, wrong key and tampering rejected, missing/invalid key refuses instead of storing clear text). Integration (real SQL Server): `SparePartStockTests` (weighted average, issue cost frozen and restored on return, no negative stock, **12 simultaneous issues of a stock of 5 spend exactly 5**, the DB CHECK on quantity), `VacationPaymentTests` (payment decided at final approval, pending reserves nothing, pooled quota across paid types, non-paid type uses none, Friday-only request refused, overlap/retroactive refused, cancel frees the period, one person cannot give both approvals, **12 simultaneous final approvals spend the 2-day quota once**, a deterministic lost-update test of `RunExclusiveForUserAsync`, a double decision succeeds once), `LoginLockoutTests` (5 wrong passwords lock for 15 min, the right one is refused meanwhile, the owner is notified, a good login resets the counter, unknown email = wrong password, an admin-set password unlocks and ends old sessions; calls `IAuthService` directly because of the HTTP rate limit), `DevicePasswordTests` (stored as `enc:v1:`, never in any response, reveal needs `RevealDevicePasswords` and is logged without the secret, an empty password on update keeps the current one). Notes for writing more: `ApiFixture` exposes `Services` (call services directly, one scope per call), `CreateRoleAsync`/`CreateUserAsync`, `AllPermissions`; **login is rate-limited to 20 per minute per client, so create one shared user per test class and give each test its own month/data** (see `VacationPaymentTests.Day`); race tests that depend on timing detect a missing lock only when cold, so keep a deterministic lock-primitive test beside them. Not covered yet: the HTTP 423 mapping of a lock, notifications, reports, map layers, maintenance state flow.
- **Definition of done for a feature:** unit tests for its pure rules, at least one integration test for its main path and boundaries, a live run with a real account (record the result), docs updated, CI green.

## API contract between the backend and the UI (2026-10-28, engineering-foundation item 8)
- **Two golden snapshots in `contract/` of this repo** (reviewed in the commit diff like the permission matrix): `permissions.json` (every permission name + the any-of policies; `Architecture.Tests/PermissionContractTests`) and `openapi.json` (the full OpenAPI document of the real app, keys sorted; `Integration.Tests/OpenApiContractTests`, needs Docker). Accept a change with `UPDATE_API_CONTRACT=1 dotnet test …` and commit the files; the failure message prints the first difference. Swagger runs with `SupportNonNullableReferenceTypes()` so `string` vs `string?` in the document is truthful (the UI types depend on it).
- **The UI repo keeps a copy** (`contract/`), syncs it with `npm run contract:sync` and generates `src/app/core/api/api-types.ts` from it (`npm run api:types`). Its CI then checks: generated types fresh, every static `api.get/post/put/delete` call has a matching route+verb in the contract, hand-written models conform to the DTOs at compile time (`Conforms<Ui, Dto>` in `*.contract.spec.ts`), and `access.ts` equals the permission catalog in both directions. Details: UI `docs/ARCHITECTURE.md`.
- **Workflow for any API change:** change the backend → update the two snapshots → in the UI `contract:sync` + `api:types` → fix what fails → commit both repos. The two CIs cannot see each other's repo, so the copy is compared by `npm run contract:check` locally (both repos side by side); skipping the sync is detected by neither CI (the UI keeps passing against its old copy) — always sync in the same working session and run `contract:check` before pushing.
- Not covered yet: integer enums (stage/kind values such as `PROJECT_STAGES`) are mirrored by hand in the UI and are not in the OpenAPI document; request bodies are not checked against UI input types (only responses).
