## Task board — assigned tasks (added 2026-09-28)
- **Two different "task" concepts — don't mix them:** `WorkTask` = a job function's fixed page (no statuses; the card opens a future page). `AssignedTask` = a task a leader sends down the hierarchy, tracked on a Kanban board (`Todo`/`InProgress`/`Done`).
- Hierarchy (Role-Permission, 2026-10-03): `AssignTaskToDepartment` → a **Department** of my branch, `AssignTaskToOffice` → an **Office** of my department, `AssignTaskToUser` → a **User** of my office. A role may hold several, so `CreateAssignedTaskRequestDto.TargetType` (`Department`/`Office`/`User`) is required when there is more than one; `Board` returns `targetTypes` + `hasScope`, and `Targets?type=` / `Targets?parentTaskId=` (delegation) list the options. A department task is handled by users of that department itself (no office) holding `HandleUnitTasks`, an office task by that office's `HandleUnitTasks` holders — `AssignedTaskRules.CanHandle`.
- Rules (`Application/Features/AssignedTasks/AssignedTaskRules.cs` is the single source): only the handler changes status (drag & drop); the creator edits (until Done) and deletes (only `Todo` with no subtasks); the handler can **delegate** (a child task with `ParentTaskId`, one level down), and the first delegation moves the parent `Todo→InProgress`. Viewing: SuperAdmin all, creator, handler, and holders of an assign/handle permission for tasks inside the unit that permission covers (`AssignedTaskRules.Scope`; the task stores `BranchId/DepartmentId/OfficeId` for this). Comments are for anyone who can view.
- History: `AssignedTaskActivity` (Created/StatusChanged/Comment/Delegated/Edited), cascades with the task. Notifications `TaskAssigned`/`TaskStatusChanged`/`TaskCommented`, `RelatedEntityType = "AssignedTask"` → UI `/task-board?task=ID` (use `router.navigateByUrl` for these links, since `navigate([...])` would encode the `?`).
- All FKs are Restrict → delete guards added to Department/Office/User delete handlers (`IAssignedTaskService.ExistsFor*`). Users tied to tasks must be deactivated, not deleted.
- API `api/AssignedTasks`: `Board?mode=incoming|outgoing|scope` (Done limited to the last 30 days), `Get/{id}`, `Targets`, `Create`, `Update/{id}`, `Status/{id}` `{status: 1|2|3}`, `Comment/{id}`, `Delete/{id}` — plain `[Authorize]`, all checks are in the rules. Migration `Add_AssignedTasks`.
- UI `features/task-board/`: `@angular/cdk` drag-drop (`cdkDropListGroup`; the enter predicate only accepts a column listed in the card's server-computed `allowedStatuses`, and the update is optimistic with revert on error). The keyboard alternative is the status switch in `TaskDetailDrawer`. Forms are in `TaskFormDialog` (create/edit/delegate).
- **Task board enhancements (2026-10-07, user approved the suggestions; migration `Task_Board_Enhancements`):**
  - **Review stage** `AssignedTaskStatus.InReview = 4` («بانتظار المراجعة», column 3 of 4; the enum value 4 sits before Done in the UI). Handler: Todo→InProgress, InProgress↔Todo/InReview. **While InReview the task is frozen for everyone but the reviewer** (user decision 2026-10-10, `AssignedTaskRules.IsFrozenFor`/`EnsureNotFrozen`): no status change (the handler can no longer pull it back), checklist, attachments, claim or links until the creator approves or returns it; comments stay open; detail DTO flag `ReviewLocked` → drawer notice. **Reviewer = creator (or SuperAdmin)**: InProgress/InReview→Done (final) or InReview→InProgress (**needs a note**, `NeedsReturnNote`; the handler cannot mark Done). `AssignedTaskRules.AllowedStatuses` is the single source (drag-drop, buttons); `PUT Status/{id}` takes `{status, note, expectedStatus?}`. **Concurrency (2026-10-10, review fix, migration `Assigned_Task_RowVersion`):** `AssignedTask.RowVersion`; every save in `AssignedTaskService` maps `DbUpdateConcurrencyException` → friendly 400; the status change and its activity row are one save; `expectedStatus` = the status the user saw (the UI always sends it) — if it changed meanwhile (e.g. returned while being approved) the decision is rejected and the board/drawer reload. Done asks for confirmation in the UI (drawer + drop). Delegation is only from Todo/InProgress.
  - **Attachments**: `AssignedTaskAttachment` (metadata) + `AssignedTaskAttachmentContent` (bytes), same pattern as vacations; PDF/JPG/PNG/Word/Excel/PowerPoint (`TaskAttachmentRules`: type from the file signature, docx/xlsx/pptx = ZIP with Office parts and **no `vbaProject.bin`**, legacy OLE only with .doc/.xls/.ppt extension), ≤ 10 files × 10 MB per task, no new permission. Anyone who can view the task attaches until Done; the uploader or the creator removes (until Done); a delegated subtask reads the parent's attachments (`ParentAttachments`, read-only; `GetTaskAttachmentQuery` allows a file if the task or any child task is viewable). Endpoints: `POST Attachments/{id}` (form `files`, 35 MB request limit; the UI uploads one file per request via `attachSequentially`), `GET Attachment/{id}?download=`, `DELETE Attachment/{id}`. Activity `Attached`/`AttachmentRemoved` + notification `TaskAttachmentAdded`.
  - **Checklist** `AssignedTaskChecklistItem` (≤ 30 items, cascade): handler or creator add/toggle/delete, only the creator edits the text; card shows `checklistDone/Total`. `POST Checklist/{id}`, `PUT|DELETE ChecklistItem/{id}`.
  - **«أتولّى» (soft claim)** `ClaimedByUserId/ClaimedAt`: informational («يعمل عليها: X»), not a lock — another handler can take over, only the claimer or the creator releases; Todo→InProgress on a department/office task auto-claims. `PUT Claim/{id}` `{claim}`. Claim/uploader FKs Restrict and are part of `ExistsForUserAsync`.
  - **Reminders**: hosted `API/Background/TaskReminderWorker` (first run 20 s after start, then `TaskReminders:IntervalMinutes`, default 10) calls `AssignedTaskReminders.RunAsync`: due today/tomorrow → `TaskDueSoon`, overdue → `TaskOverdue`, each once (`DueSoonNotifiedAt`/`OverdueNotifiedAt`, reset when the due date changes); InReview tasks notify only the creator. The migration marks already-overdue open tasks as notified so deployment doesn't flood.
- **Task board phase 2 (2026-10-08, user: "implement all"; migration `Task_Board_Planning`):**
  - **Task creation** is one place: `AssignedTaskCreator` (`CreateAsync(viewer, NewTaskSpec)`, `EnsureTargetAllowedAsync`) — used by the Create handler and by the recurring runner; `CreateAssignedTaskRequestDto.ChecklistItems` creates checklist items with the task (≤ 30).
  - **Templates** `AssignedTaskTemplate` (+items): **personal** (owner only, name unique per owner, ≤ 50), for anyone holding an `AssignTaskTo*` permission (no new permission). `GET|POST Templates`, `PUT|DELETE Templates/{id}` (delete blocked while a recurrence uses it). UI: «البدء من قالب» in the create dialog + «حفظ كقالب».
  - **Recurring tasks** `AssignedTaskRecurrence` (template + target + Daily/Weekly(day)/Monthly(day, clamped to month end) + start/end + `DueAfterDays`; ≤ 30 per owner; target id has **no FK**). `API/Background/TaskReminderWorker` runs `AssignedTaskRecurrenceRunner` before the reminders each cycle: one task per due recurrence **with the owner's current permissions**, then `NextRunDate` advances (a missed period is not back-filled — one task only). **Exactly once (2026-10-10, review fix):** `IAssignedTaskPlanningService.RunScheduledAsync` runs each due slot in one transaction with an `sp_getapplock` on `task-recurrence-{id}`, re-reads the recurrence and checks it is still active with the same `NextRunDate`, then creates the task and advances the date together — a crash before commit rolls both back, a second server instance finds the date already advanced and skips. A failure rolls back and `StopRecurrenceAsync` deactivates it (the owner is notified once). Any failure (owner lost permission/inactive, target deleted or out of boundary) deactivates that recurrence with `LastError` and notifies the owner (`TaskRecurrenceStopped`, entity `TaskRecurrence` → UI `/task-board/recurring`). `Recurrences` CRUD, `PUT Recurrences/{id}/Active` (re-checks the target), `POST Recurrences/{id}/RunNow` (extra task, schedule unchanged). UI `features/task-board/recurring-page.ts` (templates + recurrences).
  - **Links to other records** `AssignedTaskLink` (MaintenanceRequest / Vacation / Site; ≤ 10 per task; unique per task+record): adding needs the task's creator/handler **and** that the user may view the record (`TaskLinkResolver`: maintenance = `MaintenanceRules.ViewBoundary("ViewMaintenanceRequests")`, vacation = `VacationAccess.CanView`, site = any device-view permission); a viewer who can't see the record gets `available=false`, label «سجل غير متاح لك» and no data. `GET Links/{taskId}`, `POST Links/{taskId}` (`reference` = request number or id, or `entityId`), `DELETE Link/{linkId}` (adder or task creator), `GET ByLink?entityType&entityId` (only if you may view the record) — shown on the maintenance request page and the site page (`app-linked-tasks`). Vacation links open `/vacations/print/:id` only with `PrintVacation`.
  - **Stats** permission `ViewTaskStats` (migration granted it to roles holding an `AssignTaskTo*` permission): `GET Stats?from&to` over **the viewer's scope** (`AssignedTaskRules.Scope`) of tasks created in the period (default 90 days, ≤ 2 years): totals, on-time rate (done on/before due date), average days, overdue now, reviewer returns (`AssignedTask.ReturnCount`, incremented when the creator returns a task from review), per-target table and monthly created/done. UI `/task-board/stats`.
  - **Board filters / calendar / export**: `Board?doneDays` widens the done column (default 30 days, ≤ 10 years); UI filters (creator, target, due range, done age), board⇄month-calendar toggle (`localStorage ewms_task_view`), `GET Export` → xlsx (`AssignedTaskSpreadsheet`, same filters as the UI, ClosedXML like the device export).
  - Not built: tasks linked to more record types, recurring tasks with a time of day, shared templates.
