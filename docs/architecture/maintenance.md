## Maintenance: requests & tasks (added 2026-09-29)
- Entities in `Domain/Entities/Maintenance/` (namespace `Domain.Entities.Maintenance`): `MaintenanceRequest` (a repair job: client name/phone, the `DeviceMaintenance` being repaired, `DamageType`, accessories, description, `MaintenanceRequestStatus`), `DeviceMaintenance` (the physical device: name, **unique** `SerialNumber`, model, description, `DeviceType`, `DeviceCompany`), `MaintenanceTask` (a job an employee worked on: location, requesting party, required work, completed works), and 4 lookup tables (`DeviceType`, `DeviceCompany`, `DamageType`, `MaintenanceRequestStatus` with a `#RRGGBB` `Color`). Unrelated to the `Device`/`DeviceSite` inventory — don't merge them.
- **Maintenance devices (added 2026-10-04, user design):** the device data moved off the request into `DeviceMaintenances` so one device collects its whole repair history. `SerialNumber` is required, trimmed and **unique** (unique index, case-insensitive by the DB collation); the request only stores `DeviceMaintenanceId` (required, Restrict). Flow (user decision): the UI looks the device up by serial (`GET api/MaintenanceDevices/BySerial?serialNumber=` → 404 if new), creates it first if needed (`Create`), then submits the request with its id — no inline device creation inside the request. Device history = `MaintenanceRequests/GetAll?deviceMaintenanceId=` (still limited by the request view scope). Request responses keep the device fields flattened (`DeviceMaintenanceId`, `DeviceName`, `SerialNumber`, `Model`, `DeviceType*`, `DeviceCompany*`) so lists/print didn't change; the request filters `serialNumber`/`model`/`deviceTypeId`/`deviceCompanyId` now join `DeviceMaintenances` (the prefix searches seek its `SerialNumber`/`Model` indexes). The device register has **no department boundary** — access is the permission only (user: it's granted to maintenance-department users only): `ViewMaintenanceDevices` (GetAll/Get/BySerial), `CreateMaintenanceDevice`, `EditMaintenanceDevice`, `DeleteMaintenanceDevice` (blocked while the device has requests). Device types/companies in use by a device can't be deleted. Code: `Features/Maintenance/MaintenanceDevices/DeviceMaintenanceFeature.cs`, `IDeviceMaintenanceService`, `api/MaintenanceDevices`. Migration `Add_DeviceMaintenance` is **hand-written** (EF wanted to rename `DeviceTypeId` → `DeviceMaintenanceId` and drop the columns first): creates the table, makes one device per distinct trimmed serial from the existing requests (data of the latest request; an empty serial becomes `NOSN-{requestId}`), links the requests, then drops the old columns; it grants View+Create devices to roles with `CreateMaintenanceRequest`, View+Edit to roles with `EditMaintenanceRequest`, View to roles with `ViewMaintenanceRequests` (delete only SuperAdmin). Its `Down` restores the columns with their data (verified both ways). Anyone who submits/edits requests needs `ViewMaintenanceDevices` (+ `CreateMaintenanceDevice` to register new devices). **UI (2026-10-05):** page `/maintenance/devices` (`features/maintenance/devices-page.ts`: search, paging, add/edit/delete, per-device repair history modal); the request form (`request-form-dialog.ts`) no longer has device fields — the user types the serial and searches (`BySerial`), a found device is shown as a card, a 404 offers «إضافة الجهاز» (`device-form-dialog.ts`, pre-filled serial). **Adding a device requires the serial twice** (confirm field, compared trimmed and case-insensitively; copy/cut/paste/drop/context menu blocked in both fields — user decision); on edit the confirmation is needed only if the serial changes. A simultaneous duplicate serial is mapped to a friendly 400 in `DeviceMaintenanceService.SaveAsync` (unique index violation 2601/2627), and `ExceptionMiddleware` logs `KeyNotFoundException` as information (expected 404s from `BySerial`).
- **Assignment & transfer requests (2026-10-05, user decisions):** on **create**, a holder of `AssignMaintenanceRequest` may pass `AssigneeId` (an active employee of his department, `ResolveAssigneeAsync`) — that employee becomes the owner/technician and gets a `MaintenanceAssigned` notification; the creator appears only in the activity log («سجّل الطلب وأسنده إلى …»); `AssigneeId` is ignored on update (moving later = `Assign/{id}`). An employee without the permission can only create requests for himself. **Transfer requests:** the request's technician holding `RequestMaintenanceTransfer` (new; migration `Maintenance_Transfer_Requests` granted it to roles with `CreateMaintenanceRequest`) asks `POST MaintenanceRequests/TransferRequest/{id}` `{reason, suggestedUserId?}` (suggestion = colleague of the request's department; one pending per request — filtered unique index); holders of `AssignMaintenanceRequest` in that department get `MaintenanceTransferRequested`, and decide with `PUT Transfer/{transferId}/Decide` `{approve, userId?, note}` (approve = reassign to `userId` or the suggestion, same boundary as `Assign/{id}`; reject → note to the requester, `MaintenanceTransferDecided`). `GET Transfer/{requestId}` (pending for a request), `GET Transfers/Pending` (my department), `GET Transfers/Colleagues`. Entity `MaintenanceTransferRequest` (cascade with the request; user FKs Restrict and part of `ExistsForUserAsync`); activity types `TransferRequested`/`TransferRejected` (approval logs `Reassigned` with the reason). Response flag `CanRequestTransfer` (the UI has no user id). UI: «الفني المسؤول» select in the create form, `features/maintenance/transfer-panel.ts` (request page: ask dialog / decision bar) and `PendingTransfersButton` on the requests page.
- **Spare parts inventory (2026-10-05, user decisions: stock per department, issuer = request technician or department holder, weighted average cost in ل.س, low-stock notice to receivers; no per-department cost report):**
  - Entities (`Domain/Entities/Maintenance/SparePart.cs`): `SparePart` (DepartmentId, Name unique per department, PartNumber, Unit, Quantity ≥ 0 by check constraint, MinQuantity, AverageCost), optional compatibility joins `SparePartDeviceType`/`SparePartDeviceCompany` (cascade), append-only `SparePartMovement` (Receive/Issue/Return/Adjust, signed quantity, unit cost, balance after, date, note, request, user), and `MaintenanceRequestPart` (quantity + **unit cost frozen at issue**, same snapshot idea as signatures). (`DeviceType.ReplacementCostThreshold` and its alert were **removed 2026-10-08**, user decision: device types have no prices — migration `Remove_Threshold_Add_Vacation_Request_Signature`.)
  - **Quantity and average cost change only through movements**, atomically in `SparePartService`: transaction + `UPDLOCK, ROWLOCK` read of the part row, `ExecuteUpdate` of the balance, then the movement row. So two simultaneous issues can't spend the same stock, and the balance can't go negative. Receive recomputes the weighted average. Issue uses the current average. Return removes the request part and re-adds it at its frozen cost.
  - Permissions (one per operation, boundary = my department's stock, SuperAdmin all): `ViewSpareParts`, `CreateSparePart`, `EditSparePart`, `DeleteSparePart` (only without movements), `ReceiveSpareParts` (also receives the low-stock notice), `AdjustSparePartStock`, `IssueSparePart` (boundary like edit: my requests + my department's with `ViewDepartmentMaintenance`; parts only from the **request's department** stock; request must be open), `ViewSparePartReports`. Migration `Spare_Parts_Inventory` granted View+Issue to roles holding Create/EditMaintenanceRequest and the management set to roles holding `AssignMaintenanceRequest`.
  - Request lock: after «مُسلَّم»/«غير قابل للصيانة» parts can't be issued or returned. A request that ever had parts (movements point to it, even after a return) can't be deleted. Department/user delete guards: `ISparePartService.ExistsForDepartmentAsync`/`ExistsForUserAsync`.
  - Notifications: `SparePartLowStock` (crossing below MinQuantity → `ReceiveSpareParts` holders of the part's department, entity `SparePart` → UI `/maintenance/parts?part=ID`) (the old `DeviceRepairCostThreshold` notification type stays in the enum only for existing rows; it is no longer sent). Request activity types `PartIssued`/`PartReturned`.
  - API `api/SpareParts`: `Departments`, `GetAll`, `Get/{id}`, `Create`, `Update/{id}`, `Delete/{id}`, `Receive/{id}`, `Adjust/{id}`, `Movements/{id}`, `Report?from&to&departmentId`, `Request/{requestId}` (parts + device lifetime cost, policy `ViewMaintenanceRequests`), `Request/{requestId}/Available`, `Request/{requestId}/Issue`, `RequestPart/{id}` (DELETE = return). Code: `Features/Maintenance/SpareParts/SparePartFeature.cs`.
  - UI: `/maintenance/parts` (`spare-parts-page.ts` + `spare-part-dialogs.ts`: add/edit with compatibility, receive, adjust as count or damaged, movements), `/maintenance/parts/report` (stock value, most used parts, device lifetime costs per device), the «قطع الغيار» panel on the request page (`request-parts-panel.ts`: issue from available parts — compatible first — and return). Models in `core/models/spare-part.models.ts`.
- **Client = employee or external (2026-10-05, user decisions):** `MaintenanceRequest.ClientUserId` (nullable, Restrict, in `ExistsForUserAsync`) + the `ClientName`/`ClientPhone` snapshot. The person filling the form does **not** browse employees: he types the client's full name or personal ID number and `GET MaintenanceRequests/ClientLookup?query=` (any-of policy `AnyMaintenanceRequestWrite` = create/edit request) returns active employees by **exact** match only (`MaintenanceClients.FindAsync`: personal ID first, else the full name normalized for spaces/hamza/ta marbuta/alef maqsura/diacritics; several namesakes → pick by department); no match = external client (name + phone typed). On save the server re-checks the employee (`MaintenanceClients.ResolveAsync`) and takes his name (phone = typed, else his). Department cost attribution was explicitly not wanted. The employee follows his devices on `/maintenance/mine` (`GET Mine`, permission `ViewMyMaintenanceRequests` — migration `Maintenance_Client_User` granted it to **all** roles) and gets a notification on create and on every status change (entity type `MyMaintenanceRequest` → `/maintenance/mine?request=ID`). Old requests (test data) were left external. A direct `Assign/{id}` now closes a pending transfer request (`MaintenanceTransferStatus.Closed`).
- **Owner** (`UserId`) = whoever creates the record; for a request that person is also the technician (user decision). Set from the current user and never editable. `DepartmentId` is a snapshot of the owner's department at creation (like `Vacation`), so the head of that department keeps seeing it after a transfer. For a request, `StartedAt`/`CompletedAt` are **set automatically by the status stage** (see below; no manual input). Tasks still enter them manually (optional, completed ≥ started). `CreatedAt`/`UpdatedAt` are automatic.
- **Maintenance stages (user decisions 2026-10-05):** statuses stay user-defined names/colors, but each one carries a fixed `MaintenanceStage` (`Domain/Entities/Maintenance/MaintenanceRequestStatus.cs`): `New 1` / `InProgress 2` / `Ready 3` / `Delivered 4` / `NotRepairable 5` («غير قابل للصيانة» replaced the proposed «ملغى»). The stage decides behaviour, in `MaintenanceRules`:
  - `ApplyStageTimes`: New clears both times, InProgress sets `StartedAt` if empty and clears `CompletedAt`, Ready/final set `CompletedAt` (and `StartedAt` if empty).
  - **Final stages (`IsFinal` = Delivered/NotRepairable) lock the request** (`IsClosed`/`EnsureOpen`): no edit, status change, assign or transfer afterwards. A pending transfer is closed. A returning device gets a **new** request. A new request can't start in a final stage.
  - Client notifications by stage (`NotifyClientStatusAsync`): Ready «جهازك جاهز للاستلام», NotRepairable «تعذّر إصلاح جهازك», Delivered «سُلّم جهازك».
  - Responses carry `StatusStage` + `IsClosed` (all `Can*` flags false when closed). Statuses are ordered by stage, then id (board columns follow).
  - Migration `Maintenance_Status_Stages` (hand-reordered): add `Stage` (default 2), map `IsDelivery=1`→4 and the seeded names (جديد→1, قيد الصيانة→2, تم الإصلاح→3, «%غير قابل%»→5), then drop `IsDelivery`.
  - UI: the settings page has a stage select. The request form has no date inputs and hides final statuses on create. **Moving to a final stage always asks for confirmation** (`finalStageConfirm` in `maintenance.models.ts`): on the details page, in the edit form, and on board drag-drop (on cancel the card stays put). A closed request shows a 🔒 notice.
- **Scope** (`Application/Features/Maintenance/MaintenanceRules.cs`, single source): a record is visible/editable/deletable by its owner, holders of `ViewDepartmentMaintenance` for records of their department (edit/delete still need `Edit…`/`Delete…`), and SuperAdmin. The policy decides *which operation*, the rules decide *which records*.

Rules: `MaintenanceRules.Boundary`/`Scopes` (view/edit/delete = own + department with `ViewDepartmentMaintenance`; assign = my department; SuperAdmin all). Migrations: `Add_Maintenance_Activity_Signature` copied with its original id (DBs that ran it on `test` skip it) + `Maintenance_Extension_Permissions` (permissions + grants to the legacy `Manager` role).
- **Split permissions (2026-10-03):** `ChangeMaintenanceStatus` (`Status/{id}`; changing the status through the edit form also needs it — `EditMaintenanceRequest` alone can edit the other fields; response flag `CanChangeStatus`), `ViewMaintenanceStats` (`Stats`; covers my records, plus my department's with `ViewDepartmentMaintenance`), `ToggleUserActive` (changing `IsActive` in `UpdateUserCommandHandler`; SuperAdmin always). Migration `Split_Status_Stats_Toggle_Permissions` granted each to the roles that held `EditMaintenanceRequest` / `ViewMaintenanceRequests`+`ViewMaintenanceTasks` / `EditUser`.
- **Permissions — one per operation** (user decision 2026-09-29): tasks `ViewMaintenanceTasks`/`CreateMaintenanceTask`/`EditMaintenanceTask`/`DeleteMaintenanceTask`; requests `ViewMaintenanceRequests` (view + search + technicians)/`CreateMaintenanceRequest`/`EditMaintenanceRequest`/`DeleteMaintenanceRequest`; the 4 lookup tables share `ViewMaintenanceLookups`/`CreateMaintenanceLookup`/`EditMaintenanceLookup`/`DeleteMaintenanceLookup` (the View one was added 2026-09-30 — anyone filling or searching requests needs it for the dropdowns). Policies are registered in a loop in `AddAPIRigstrationServices.cs`. Only SuperAdmin has them by default — grant them to roles from the Roles page. The first version had grouped permissions (`ManageMaintenanceTasks`, `ManageMaintenanceLookups`, Edit = edit+delete); migration `Split_Maintenance_Permissions` inserts the new ones, copies every existing grant to its per-operation equivalents, and deletes the old ones — follow that pattern for future permission renames (the seeder only adds). 5 default statuses are seeded once (only if the table is empty).
- **Search** `GET api/MaintenanceRequests/GetAll` (paged `PagedResultDto<T>`, pageSize ≤ 100, newest first), filters AND-combined: `deviceMaintenanceId` (one device's history), `serialNumber`/`model` = **starts with** on the request's device (`LIKE 'x%'` → index seek on `IX_DeviceMaintenances_SerialNumber`/`_Model`, then joined), `clientName` = **contains** (scans the narrow name index), and exact `deviceCompanyId`/`technicianId`/`deviceTypeId`/`damageTypeId`/`statusId` (composite `(FK, CreatedAt)` indexes). Don't switch serial/model to `Contains` — it drops the seek. If "contains" on large volumes gets slow, the next step is SQL Server Full-Text Search (not available on LocalDB). `GET api/MaintenanceRequests/Technicians` feeds the technician filter.
- Layout follows the compact AssignedTasks style: one file per lookup (`Features/Maintenance/<Lookup>/<Lookup>Feature.cs` = records + validators + one handler), `Requests/MaintenanceRequestCommands.cs` + `...Queries.cs`, `Tasks/MaintenanceTaskFeature.cs`; DTOs in `DTOs/Request/MaintenanceRequestDtos.cs` / `DTOs/Response/MaintenanceResponseDtos.cs`; one `MaintenanceProfile`; JSON (`[FromBody]`) bodies. Controllers: `api/DeviceTypes`, `api/DeviceCompanies`, `api/DamageTypes`, `api/MaintenanceRequestStatuses`, `api/MaintenanceDevices`, `api/MaintenanceRequests`, `api/MaintenanceTasks`.
- All FKs Restrict → delete guards: lookups in use can't be deleted; User and Department delete handlers check `IMaintenanceRequestService`/`IMaintenanceTaskService.ExistsFor*`. Migration `Add_Maintenance`.
