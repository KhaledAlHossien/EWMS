## Device inventory: Site → Device (added 2026-09-28; regions replaced by governorates 2026-10-03)
- Documentation/inventory feature (replaces scattered Excel sheets). **v1.1.0 (2026-10-11, user decisions — «any service is a permission; what an employee adds belongs to his department and branch»):**
  - **Sites = a shared, unique registry for every branch** (one site, several branches may use it). Own permissions `ViewSites`/`CreateSite`/`EditSite`/`DeleteSite`, boundary = all sites; reads use the any-of policy `AnySiteView` (site permissions + any device permission, because the installation form picks a site). `GET Sites/Nearby?latitude&longitude&excludeId` = sites within 200 m (`GeoRules.DistanceMeters`) → warning in the site form. Delete blocked while installations or layer entries (v1.2.0) exist.
  - **An installation (`DeviceSite`) belongs to the department + branch of whoever added it** (`BranchId`/`DepartmentId`, nullable, FK Restrict + delete guards on department/branch). Boundary `DeviceInventoryRules.ScopeFor(viewer)` → `InstallationScope`: organization-wide (`ViewOrganizationDashboard`/SuperAdmin) = all; `ViewBranchDevices` = my branch; otherwise my department; no unit = nothing. Search/Get/IpInUse/Export/History/Edit/Delete/Verify/Password all apply it (`EnsureInScope`); site installation counts too. Create/Import take the creator's unit, or `DepartmentId` chosen by an organization-wide user (any department) or a `ViewBranchDevices` holder (departments of his branch) — the UI shows the «القسم المالك» select only to them; edit can move it (logged as «القسم»). The device **catalog stays shared** (counts are global).
  - Migration `Sites_Permissions_Installation_Units` adds the columns, inserts the 5 permissions and copies grants (`ViewSites` ← any device permission, Create/Edit/DeleteSite ← Create/Edit/DeleteDevice, `ViewBranchDevices` ← any device permission so current users keep seeing their branch). `DbSeeder.BackfillInstallationUnitsAsync` (every startup, rows with no branch only) takes the unit from the installation's Created/Imported log user, else from the legacy `DeviceInventory:OwnerDepartmentId` if that department exists; the rest show «بلا قسم» until an organization-wide user picks a department.
  - `CreateDevice`/`EditDevice`/`DeleteDevice` are plain policies; device reads use `AnyDeviceView` (+ `ViewBranchDevices`). The old `DeviceAccessRequirement`/`DeviceAccessService`/`Devices/MyAccess`/`inOwnerDepartment` were removed in the 2026-10-05 review. **`DeviceInventory:OwnerDepartmentId` is no longer used** except as that one-time backfill fallback.
  - UI: sidebar section «الخريطة والمواقع» (المواقع, guarded by `SITE_ACCESS`); «توثيق الأجهزة» keeps التركيبات/الأجهزة (`DEVICE_ACCESS`); `DeviceService.siteAccess` vs `access` (+ `canChooseUnit`); installations table has a «القسم» column. Roles page section «الخريطة والمواقع» (site permissions + `ViewBranchMap`).
- **Review 2026-10-05 (user approved all items):** code in `Application/Features/DeviceInventory/` (`SiteFeature`, `DeviceFeature`, `InstallationFeature`, `DeviceInventoryRules` = single source for validation/mapping/log diff); JSON bodies; migration `Device_Inventory_Review`.
  - **Passwords:** `DeviceSite.Pass` is **encrypted** with AES-GCM (`Infrastructure/Security/DevicePasswordProtector`, prefix `enc:v1:`). The key is `DeviceInventory:PasswordKey` in appsettings (32 bytes Base64; user decision: config file like the JWT key). **Losing the key loses every password: back it up and move it to server env vars before deployment.** `DbSeeder.EncryptDevicePasswordsAsync` encrypts leftover plain rows at startup. Passwords are **never in a list or DTO** (`hasPassword` only). `GET DeviceSites/Password/{id}?copy=` needs the new permission `RevealDevicePasswords` (granted by the migration to roles holding `EditDevice`, user decision), sends `no-store`, and logs every show/copy. Update with an empty `pass` keeps the current password.
  - **Change log** `DeviceInventoryLog` (entity type + id, action Created/Updated/Deleted/PasswordRevealed/PasswordCopied/Verified/Imported, readable title, field-by-field «قديم ← جديد» details, password only «تغيّرت»; user Restrict → user-delete guard). Exposed by `{Sites|Devices|DeviceSites}/History/{id}`. UI: `app-device-history` modal.
  - **Concurrency:** `RowVersion` on Site/Device/DeviceSite. Responses carry `rowVersion` and updates send it back. A stale save, and a duplicate unique key from a concurrent insert, both return a friendly 400 (`DeviceInventorySave`).
  - **Validation** (`Application/Common/NetworkRules` ⇄ UI `core/utils/network.ts`, change together): IPv4 without leading zeros, contiguous subnet mask, optional gateway inside the device subnet, MAC normalised to `AA:BB:CC:DD:EE:FF`, VLAN 1–4094. Names are trimmed. The catalog's `(Name, Model)` is unique; the migration merged existing duplicates first.
  - **New fields:** installation `Gateway`, `MacAddress`, `Port`, `Vlan`, `Firmware`, `InstallDate`, `LastVerifiedAt` (`PUT DeviceSites/Verify/{id}` = «✓ تحققت»), and `Status` (1 يعمل / 2 معطّل / 3 أُزيل). User decision: «أُزيل» for dismantled devices; delete stays for input mistakes. Site `ContactName`, `ContactPhone` (PhoneRules), `ResponsibleParty` (free text). Device `Category` (free text + suggestions), `Manufacturer`.
  - **Server search:** `GET DeviceSites/Search?q&governorateCode&siteId&deviceId&status&page&pageSize(≤200)` returns each row's `duplicateIp` flag. `DeviceSites/IpInUse` feeds the form warning. `Sites/GetAll` and `Devices/GetAll` return installation counts, so pages no longer load every installation. The old `DeviceSites/GetAll` and `Sites/{id}/Devices` were removed.
  - **Excel (ClosedXML):** `DeviceSites/Export` (same filters, **no passwords**), `ImportTemplate` (red = required, instructions sheet), `Import?dryRun=true|false` (≤2000 rows, 5 MB; columns read by header name). User decision: the site must already exist, otherwise the row is rejected; an unknown device (name + model) is added to the catalog. A preview saves nothing; commit saves only the valid rows, in one transaction. UI: `app-installations-import`.
  - **UI:** IP has a ↗ link that opens `http://ip`; the site page and map use the server `governorateCode` (no client point-in-polygon). Clicking a map site without a device view permission shows a toast instead of a denied page.
- Entities (`Domain/Entities`): `Site` (Name*, Description, Latitude*, Longitude*, `GovernorateCode`). **There is no `Region` entity/table any more** (user decision 2026-10-03, migration `Replace_Regions_With_Governorates`, which first appended each site's old region name to its description): the "region" of a site is one of the 14 fixed Syrian governorates, **derived by the server from the coordinates on every create/update** (`Features/Sites/GovernorateResolver` → `Application/Common/Governorates`, which embeds a copy of `public/maps/syria-governorates.geojson` — keep both files in sync; a point outside every governorate is rejected with an Arabic message). The client never sends it; responses carry `governorateCode`/`governorateName`. `DbSeeder.BackfillSiteGovernoratesAsync` fills legacy sites from their coordinates at startup; UI filter lists come from `core/constants/governorates.ts`. Coordinates are nullable in the DB (legacy rows) but required by the validators, inside Syria's bounds (`Application/Common/GeoRules`). The old free-text `Site.Location` was dropped by migration `Add_Map_Coordinates_InstallLocation`, which first parsed "lat, lng" text into the new columns and appended any other text to `Description`. `Device` (Name*, Model, Description) is a standalone **type/model**; `DeviceSite` is the many-to-many join table between `Device` and `Site` (a device can be installed at multiple sites, a site can host multiple devices) and carries the per-installation info: `SN` (serial number of the physical unit — moved off `Device` by migration `Move_SN_To_Installation`, which copied each device's SN to its installations and kept orphan SNs in the device description), `InstallLocation` (precise spot inside the site, e.g. "عند البوابة الرئيسية"), `Ip*`, `SubnetMask*` (both validated as IPv4 in the command validators), `UserName*`, `Pass*`, `Note`. **`Device` is a reusable type/model, not a physical unit** (user correction 2026-09-29): the same device can be installed several times at the same site with different IP/credentials — there is **no** uniqueness on `(DeviceId, SiteId)` (dropped by migration `Allow_Repeated_Device_Per_Site`, and the `ExistsLinkAsync` handler checks were removed). Don't re-add it.
- UI (`features/devices/`, routes guarded by `deviceGuard`). **In the sidebar since 2026-10-03** (user decision, replacing the old dashboard `DeviceShortcuts` frame, which was deleted): a "توثيق الأجهزة" section (التركيبات / المواقع / الأجهزة — صفحة المناطق حُذفت) shown to anyone holding any device permission (`DEVICE_ACCESS` in `core/constants/access.ts`, same group guards the `/devices` route): three pages — `devices/installations` (main page: governorate→site→device filters, search by IP/SN/user, password masked with show + copy for every viewer — user choice), `devices/sites` (location rendered as a Google Maps link when it's coordinates/URL), `devices/catalog`. Manage buttons only when `canManage`.
- Same IP twice at the same site is **allowed, only warned** in the UI (live warning under the IP field + ⚠ badge in the table) — user decision 2026-09-29; don't add a backend block.
- `Site.Name` is globally unique (like `Office.Name`); `Device.Name`/`SN` are not — multiple devices can plausibly share a name/model, so no uniqueness is enforced there.
- Delete guards (matching the Office/Department pattern): can't delete a `Site` with `DeviceSite` links (`HasDeviceLinksAsync`), can't delete a `Device` with `DeviceSite` links (`HasSiteLinksAsync`) — all throw a friendly `InvalidOperationException` instead of a raw FK-restrict 500.
- Endpoints: `api/Sites` and `api/Devices` (`GetAll`/`Get/{id}`/`Create`/`Update/{id}`/`Delete/{id}`/`History/{id}`), and `api/DeviceSites` (`Search`/`Get/{id}`/`IpInUse`/`Create`/`Update/{id}`/`Delete/{id}`/`Password/{id}`/`Verify/{id}`/`History/{id}`/`Export`/`ImportTemplate`/`Import`). All take JSON bodies; see the review bullet above.
- Migration `Add_DeviceInventory` creates all four tables in one migration (no existing data to backfill, unlike `Add_User_OfficeId`).
