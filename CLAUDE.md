# EWMS — Employee Workflow Management System

Internal HR system: branches, departments, offices, users, roles/permissions, and a multi-stage **vacation request workflow**.

Org hierarchy: **Branch → Department → Office → User**. `Vacation` approval scoping deliberately stays at Department/Branch level only — it does NOT use Office (confirmed with the user 2026-09-27).
The old "Projects" feature was removed in commit `ba670e2` and replaced by Vacations.
Code comments and user-facing messages are in Arabic; keep that convention.

## Stack
- Backend: ASP.NET Core **.NET 10**, EF Core 10 + SQL Server (LocalDB, DB name `EWMS`), MediatR 12, FluentValidation 12, AutoMapper 16, JWT Bearer, BCrypt.
- Frontend: **Angular 22** standalone components. **Active UI is `F:\-EWMS-UI-main-main`** (separate folder, not a git repo; chosen by the user 2026-09-27). `EWMS.Client/` from older notes does not exist here.
- Solution file: `EWMS.slnx` (API, Application, Domain, Infrastructure). `EWMS/Class1.cs` is an empty leftover, not in the solution.

## Architecture (Clean Architecture + CQRS)
Dependencies: `API → Application, Infrastructure`; `Infrastructure → Application, Domain`; `Application → Domain`.

- **Domain/** — entities (`User`, `Branch`, `Department`, `Office`, `Role`, `Permission`, `RolePermission`, `Vacation`, `VacationType`, `UserToken`) and `Enums/VacationStatus`. `User.BranchId/DepartmentId/OfficeId` are **nullable and role-dependent** (see "User placement by role" below); `Office.DepartmentId` is required (belongs to exactly one department).
- **Application/**
  - `Features/<Feature>/Commands|Queries/<Action>/` → `XxxCommand` (IRequest), `XxxCommandHandler`, `XxxCommandValidator`.
  - `DTOs/Request`, `DTOs/Response`, `Helper/Profiles` (AutoMapper), `Interfaces/` (`IXxxService`).
  - `Common/Behaviors/ValidationBehavior` runs all FluentValidation validators in the MediatR pipeline.
  - Registered in `AddApplicationRegistrationServices.cs`.
- **Infrastructure/**
  - `Persistence/Data/DataContext.cs` (relationships, indexes, mostly `DeleteBehavior.Restrict`), `DbSeeder.cs`, `Migrations/`.
  - `Persistence/Repositories/*Service.cs` implement the Application interfaces (they are services/repositories over `DataContext`).
  - `AddInfrastructureRigstrationServices.cs` — DI + JWT config.
- **API/**
  - `SystemBuild/Program.cs` (entry; auto-runs migrations + seeding on startup), `AddAPIRigstrationServices.cs` (Swagger + authorization policies), `ApplicationPipeline.cs`.
  - `Controllers/` — thin, only call `_mediator.Send(...)`.
  - `Middlewares/ExceptionMiddleware.cs` maps exceptions → HTTP: `KeyNotFoundException`→404, `ArgumentException`/`InvalidOperationException`→400, `UnauthorizedAccessException`→401, `ValidationException`→400 with errors list. **Handlers signal errors by throwing these.**

Request flow: Controller → MediatR → ValidationBehavior → Handler → `IXxxService` → EF Core.

### Adding a new feature (follow existing pattern)
1. Entity in `Domain/Entities`, DbSet + config in `DataContext`, add migration (`dotnet ef migrations add <Name> -p Infrastructure -s API`).
2. Interface in `Application/Interfaces`, implementation in `Infrastructure/Persistence/Repositories`, register in Infrastructure DI.
3. DTOs + AutoMapper profile + Commands/Queries/Handlers/Validators under `Application/Features/<Feature>`.
4. Controller in `API/Controllers`; if a new permission is needed: add it to `Application/Common/AppPermissions.cs` only (one per operation: `ViewXs`/`CreateX`/`EditX`/`DeleteX`) — the policy and the DB row + SuperAdmin grant are generated from it.

## Auth & permissions
- `POST api/Auth/login` → JWT with claims: NameIdentifier (UserId), Email, Name, Role, `DepartmentId`, `BranchId`.
- Tokens are stored in `UserTokens`; `OnTokenValidated` rejects revoked/expired tokens, so logout really revokes.
- Current user: `ICurrentUserService` (also `IUserService.UserId`) reads claims.
- **Access model = Role-Permission only (user decision 2026-10-03, branch `Test_2`).** The user creates **one role per person** and grants it permissions; nothing is inferred from a role's name or from the user's placement (having an `OfficeId` does not make anyone "head of office"). A role is only a **permissions template** — it has no unit. The user's placement (branch / department / office) is set on the **user form** (final decision 2026-10-03, replacing the short-lived "unit on the role" design): all three are optional, `UserRules.EnsureUserReferencesAsync` derives the higher level from the lower (office → department → branch) and rejects conflicts; `SuperAdmin` has no unit. Users must re-login after a placement change (the JWT carries `DepartmentId`/`BranchId`, but all rule checks read the user from the DB).
  - **Every permission carries a fixed record boundary, coded in the handler and stated in its Arabic description** — never a configurable scope (the user explicitly rejected scopes). A different boundary = a new permission. Handlers read permissions via `Application/Common/Viewer` (`Viewer.CurrentAsync(IUserService, IUserPermissionService)`, `Has()`, `IsSuperAdmin`); `IUserPermissionService` (Infrastructure `UserPermissionService`) reads the role's permissions **from the DB by user id** (cached per request) and finds holders (`GetUsersWithPermissionAsync(permission, branch/department/office, exactUnit)`) for notifications. `PermissionAuthorizationHandler` and `DeviceAccessService` use it too, so role/permission changes apply immediately.
  - `OrganizationRole` now only has `IsSystemAdmin` (by role name `SuperAdmin`, which can't be renamed or deleted) plus `IsInDepartmentItself`/`IsInOffice` unit comparisons. Don't reintroduce position inference.
  - Boundaries: vacations — `ViewVacations` own, `ViewDepartmentVacations` my department, `ViewBranchVacations` my branch (+ stats page), `ApproveVacationFirst`/`ApproveVacationFinal` my branch (given to the branch's administrative staff, not necessarily department heads); dashboards — `ViewBranchDashboard` (branch + its departments/offices), `ViewDepartmentDashboard` (department + offices), `ViewOfficeDashboard`; task board — `AssignTaskToDepartment` (departments of my branch), `AssignTaskToOffice` (offices of my department), `AssignTaskToUser` (users of my office), `HandleUnitTasks` (tasks assigned to my own unit); maintenance — `ViewDepartmentMaintenance` (records of my department; edit/delete still need their own permission); work-task card view — assignee, or `ViewWorkTasks`/any dashboard permission in the same branch.
  - Migrations: `Add_Role_Organizational_Unit` (kept because it may already be applied on a dev DB) is undone by `Remove_Role_Organizational_Unit`, which first copies a role's unit to its users that have no placement. `Role_Permission_Only`: adds `Vacation.FirstApprovedByUserId` (the same person can't approve both stages; they get the final-decision notice), inserts the new permissions, splits `ApproveVacation` (legacy `Manager` → First, `BranchManager` → Final, others → both), grants the legacy-named roles exactly what their name used to imply, and deletes the `Module.*`/`ViewModuleAssignments`/`EditModuleAssignments`/`ViewAssignedTasks`/`CreateAssignedTask` rows left by the abandoned `test` branch.
  - Delete guard added: a user with vacations or vacation decisions cannot be deleted (`IVacationService.ExistsForUserAsync`) — deactivate instead. The `SuperAdmin` role cannot be renamed or deleted.
- Authorization = named policies (`[Authorize(Policy = "CreateUser")]`) checked by `API/Authorization/PermissionAuthorizationHandler` (see above). Endpoints whose permission is "any of several" (vacation view/approve, task board, dashboards) use plain `[Authorize]` and check in the handler. `GET api/Auth/Permissions` returns `{ permissions }` for the UI to refresh without re-login.
- Seeded roles: only `SuperAdmin` on a fresh DB (user decision on `Test_2`); every other role is created from the Roles page (which has "نسخ دور" to start from a similar role). Older DBs still have the legacy `BranchManager`/`Manager`/`OfficeManager`/`Emp` roles (they keep working; the migration `Role_Permission_Only` gave them the permissions their names used to imply). Seeded admin user is in `DbSeeder.cs`.
- **Permissions are one per operation, everywhere** (user decision 2026-09-30; no `Manage…` permission exists any more). **Single source: `Application/Common/AppPermissions.cs`** (59 names + Arabic descriptions) — `DbSeeder` inserts missing ones, `AddAPIRigstrationServices` registers a same-named policy for each in a loop. Every policy used in a controller must be in that list; the reverse no longer holds — permissions that only set record boundaries (see the access model above) are checked in handlers.
  - Users `ViewUsers`/`CreateUser`/`EditUser`/`DeleteUser` (`Auth/register` = `CreateUser`); Branches `ViewBranches`/`CreateBranch`/`EditBranch`/`DeleteBranch`; Departments `ViewDepartments`/`CreateDepartment`/`EditDepartment`/`DeleteDepartment`; Offices `ViewOffices`/`CreateOffice`/`EditOffice`/`DeleteOffice`; Roles `ViewRoles` (incl. `Roles/Permissions`)/`CreateRole`/`EditRole`/`DeleteRole`; Vacations `ViewVacations`/`CreateVacation`/`CancelVacation`/`ApproveVacation` (approve + `PendingForMe`); Vacation types `ViewVacationTypes`/`CreateVacationType`/`EditVacationType`/`DeleteVacationType`; Work tasks `ViewWorkTasks`/`CreateWorkTask`/`EditWorkTask`/`DeleteWorkTask`; Device inventory `ViewDevices`/`CreateDevice`/`EditDevice`/`DeleteDevice` (one set for regions+sites+devices+installations); Maintenance — see its section.
  - **Every read has a View permission too, including form lookups** (user decision 2026-09-30, reversing the first version where they were open): `ViewDepartments` (`Department/Get|GetAll`), `ViewVacationTypes` (`VacationTypes/Get|GetAll`), `ViewMaintenanceLookups` (the 4 maintenance lookup controllers). So a role needs the lookup View permission next to the create/edit permission that uses it: vacation form → `ViewVacationTypes`; maintenance request form/search → `ViewMaintenanceLookups`; any branch/department picker (incl. the UI `getBranchLookup()`) → `ViewDepartments`. Migration `Add_View_Permissions_For_Lookups` granted them to the roles that relied on those reads at the time (`ViewDepartments` → every role, `ViewVacationTypes` → roles with vacation permissions, `ViewMaintenanceLookups` → roles with maintenance-request/lookup permissions). View permission names are plural (`ViewXs`).
  - **No permission policy on the controller (checked in handlers instead):** `AssignedTasks` (`AssignTaskTo*`/`HandleUnitTasks`), `Dashboard` (`View*Dashboard`, `ViewBranchVacations`/`ViewDepartmentVacations` for `Vacations`), vacation view/approve endpoints, `WorkTasks/My|View`; and truly open to any signed-in user: `Map` (SuperAdmin only inside), `Notifications`, `Auth/Me`, `Auth/Permissions`, `Devices/MyAccess`.
  - The permission only opens the operation; record-level scoping still lives in the handlers/rules (`UserRules`, `OfficeRules`, vacation handlers, `MaintenanceRules`, department delete = own branch).
  - Privilege-escalation guard: a non-SuperAdmin can't grant a role holding `CreateBranch`/`EditBranch`/`DeleteBranch` (`AppPermissions.IsBranchManagement`, used by role create/update, `UserRules`, `AuthService.RegisterAsync`).
- **Role grants:** SuperAdmin gets **every** permission on each startup (`DbSeeder`). The other seeded roles get defaults **only when the role row is first created** (fresh DB: vacation permissions + `ViewDepartments` + `ViewVacationTypes`) — after that the seeder never touches them, so the user's edits from the Roles page stick (user decision 2026-09-30: "I'll adjust the other roles myself"). Don't reintroduce per-startup grants for non-SuperAdmin roles.
- Renaming/removing a permission needs a migration (the seeder only adds): insert new rows, copy each role's grants old→new, delete the old rows (cascade). See `Split_Maintenance_Permissions` and `Split_All_Permissions` (the latter also dropped `ManageVacations`, which never guarded any endpoint, and the dead "Project" policies were removed from the API).
- UI (`F:\-EWMS-UI-main-main`, branch `test`) follows the same names: `core/constants/access.ts` mirrors `AppPermissions` (plus groups `APPROVE_VACATIONS`, `VACATION_STATS`, `TASK_OVERSIGHT`), `permissionGuard` accepts only `data.permission` / `data.anyPermission` (no role names), the home dashboard is picked by `View*Dashboard` permission, and the task board needs `ViewTaskBoard` (sidebar, route and the whole `AssignedTasks` controller; migration `Add_ViewTaskBoard_Permission` granted it to roles holding any assign/handle permission and to the legacy named roles) and shows a target-type selector when a role holds several `AssignTaskTo*`.

## Vacation business rules (core domain) — reviewed & hardened 2026-09-27
- Status flow: `PendingManager (1)` → `PendingBranchManager (3)` → `Approved (4)`; any stage can → `Rejected (5)` (stores RejectedByUserId, reason, date).
  `PendingAdministrative` was removed entirely 2026-09-27 (enum member, translations, `GetPendingForAdministrativeAsync`, and the status conditions in `VacationService`'s day-count/overlap queries). Its old int value (`2`) is left unassigned/reserved in the enum comment — never reuse it.
  A `Cancelled (6)` status was added the same day: the vacation's owner can cancel it (soft — `Status = Cancelled`, record kept for audit) only while it's `PendingManager` or `PendingBranchManager`; blocked once `Approved`/`Rejected`/already `Cancelled`. Endpoint: `PUT api/Vacations/Cancel/{id}`, policy `CancelVacation`. `Cancelled` is intentionally excluded from `HasOverlappingVacationAsync` and the paid/unpaid day-count queries — cancelling frees up that period and doesn't count against the monthly quota.
- Approver checks (`ApproveVacationCommandHandler`, rules in `Features/Vacations/VacationAccess.cs`, 2026-10-03): stage 1 (`PendingManager`) needs `ApproveVacationFirst`, stage 2 (`PendingBranchManager`) needs `ApproveVacationFinal`, both limited to vacations of **the approver's branch**; whoever approved stage 1 (`FirstApprovedByUserId`) can't also give the final approval; `SuperAdmin` bypasses all. Self-approval is blocked for everyone except SuperAdmin. (The enum names `PendingManager`/`PendingBranchManager` are historical — they mean first/final stage.)
- Create (`CreateVacationCommandHandler`): **SuperAdmin and anyone without a department cannot submit vacations** (`InvalidOperationException`; UI hides the form). The vacation of someone who holds `ApproveVacationFirst` **skips stage 1** and starts at `PendingBranchManager`. End ≥ start, no overlap with pending/approved vacations, `VacDayCount = days inclusive`, Department/Branch copied from the user. **Returns `List<VacationResponseDto>`, not a single one** — see paid-day splitting below.
- Paid rule (day-level splitting, confirmed with user 2026-09-27): if `VacationType.IsPaid == false` → whole request unpaid. Otherwise max **2 paid days per month, pooled across all IsPaid=true types** (regular paid + sick + overtime-reward share the same monthly cap). If a single request would cross the cap mid-range, `BuildPaidUnpaidSegmentsAsync` walks day-by-day and **splits it into separate `Vacation` rows** — one covering the still-available paid days, another (or more, if it spans several months) covering the rest as unpaid. Each resulting row goes through the normal independent approval workflow.
- Visibility (`VacationAccess`): `GetAll` = my own + my department's (`ViewDepartmentVacations`) or my branch's (`ViewBranchVacations`, or either approval permission); `GetById`/`User/{userId}` apply the same rule per record/user; `PendingForMe` = stage-1 vacations of my branch (`ApproveVacationFirst`) + stage-2 ones (`ApproveVacationFinal`, minus those I approved in stage 1), never my own.
- Notifications (`VacationNotifier`) go to permission holders in the vacation's branch (`IUserPermissionService.GetUsersWithPermissionAsync`): submit → First approvers (or Final ones if it skipped stage 1); first approval → employee + Final approvers; any rejection → employee (+ the first approver on a final decision); final approval → employee + first approver; cancel → First approvers before stage 1, first approver + Final approvers after.
- Endpoints (`api/Vacations`): `Create` (policy `CreateVacation`), `Cancel/{id}` (policy `CancelVacation`, owner-only), `My` (policy `ViewVacations`); `Approve/{id}` (PUT body `{approve, reason}`), `PendingForMe`, `Get/{id}`, `GetAll`, `User/{userId}` are plain `[Authorize]` with the checks above in the handlers.

## Offices (added 2026-09-27)
- CRUD at `api/Offices` (`Create`/`Update`/`Delete`/`Get/{id}`/`GetAll`), policies `CreateOffice`/`EditOffice`/`DeleteOffice`/`ViewOffices`. Scoping (`Offices/OfficeRules`): a user with a department (Manager) manages only their department's offices; a user without one (BranchManager) manages offices of every department in their branch; SuperAdmin everything.
- **User placement by role** (decided with the user 2026-09-27, `Application/Features/Users/UserPlacement.cs`, mirrored in UI `core/utils/user-placement.ts` — change both together):
  SuperAdmin → no branch/department/office; BranchManager → branch only; Manager → branch + department (no office); Emp and any custom role → branch + department + office.
  `UserRules.EnsureUserReferencesAsync` validates only what the role needs (office ∈ department ∈ branch) and returns the normalized placement — fields the role doesn't need are dropped to NULL even if sent. Migration `Make_User_Placement_Optional` made the columns nullable and NULLed existing data to match. JWT `DepartmentId`/`BranchId` claims are empty (→ 0 in `ICurrentUserService`) when absent; users must re-login after their placement changes.
  Legacy `POST api/Auth/register` (`AuthService.RegisterAsync`, unused by the UI) still requires all three — not migrated to this rule.
- Vacation notifications exclude the requester from manager recipient lists, and dept Managers only get final-decision/cancel notices if the vacation actually passed through them (`ManagerAccept`).
- Deleting a Department/Office that still has children throws a friendly `InvalidOperationException` (`HasOfficesAsync` / `HasUsersAsync` checks) rather than letting the DB FK-restrict raise a raw 500 — **always add this guard for any new parent→child relationship**, it's easy to forget.
- Migration `Add_User_OfficeId` was hand-edited (not left as EF auto-generated) because the DB already had existing Users: it adds the column nullable, backfills a "مكتب افتراضي - <Department>" placeholder office + assigns existing users to it, then tightens to NOT NULL. Any future required-FK-on-populated-table migration should follow this same backfill pattern.

## Notifications (added 2026-09-27)
- New `Domain.Entities.Notification` (recipient `UserId`, `Title`, `Message`, `Type` enum, optional `RelatedEntityType`/`RelatedEntityId` for deep-linking, `IsRead`/`ReadAt`). Cascade-deletes with its recipient `User`.
- **Real-time push via SignalR (added 2026-09-27).** Hub `API/Hubs/NotificationHub` at `/hubs/notifications` (`[Authorize]`, server→client only, method name `notification`, payload `NotificationResponseDto`). Routing is `Clients.User(UserId)` via the default NameIdentifier user-id provider.
  - Push is automatic: Infrastructure `NotificationService.AddAsync/AddRangeAsync` call `INotificationPusher` (Application interface, implemented by `API/Hubs/SignalRNotificationPusher`, registered in `AddAPIRigstrationServices`) **after** SaveChanges. Push failures are logged and swallowed — the DB row is the source of truth. So any new notifier gets real-time for free; don't call the hub directly.
  - JWT over websocket: `OnMessageReceived` accepts `?access_token=` **only** for `/hubs/*`, and `OnTokenValidated` falls back to that query token so the revoked-token check still applies. An already-open socket is not killed on logout; the client stops it itself.
  - UI: `NotificationService.start()` (SignalR + auto-reconnect, 60s fallback poll of `UnreadCount`), toast popups (`features/layout/notification-toasts.ts`), browser desktop `Notification` when the tab is hidden (opt-in button on the notifications page). `proxy.conf.json` has a `/hubs` entry with `ws: true` — changing it requires restarting `ng serve`.
- `Application/Features/Vacations/VacationNotifier.cs` is a static dispatch helper (same pattern as `UserRules`) called from `CreateVacationCommandHandler`, `ApproveVacationCommandHandler`, and `CancelVacationCommandHandler`. It resolves recipients by role+department/branch via the existing `IUserService.GetByDepartmentAsync`/`GetByBranchAsync` (filtered client-side to `Role.Name == "Manager"`/`"BranchManager"`) — no new user-lookup repo methods were needed.
- Full trigger map (verified live end-to-end): submit → dept Manager(s); Manager approves → employee + branch Manager(s) (forwarded); Manager rejects → employee only (branch never sees it); BranchManager approves (final) → employee + dept Manager(s); BranchManager rejects (final) → employee + dept Manager(s); employee cancels → dept Manager(s) always, **plus** branch Manager(s) too if it had already reached `PendingBranchManager`.
- A `CreateVacationCommand` that splits into paid+unpaid segments (see above) fires one `VacationSubmitted` notification per segment/entity created.
- Endpoints (`api/Notifications`, plain `[Authorize]`, every action implicitly scoped to the caller): `GET My?unreadOnly=`, `GET UnreadCount`, `PUT MarkAsRead/{id}` (403/401 if not the owner), `PUT MarkAllAsRead`.
- If you add a new workflow with async multi-party approval later, follow this same shape: a `Notification` row per recipient, a static `<Feature>Notifier` helper, called from inside the command handler right after `UpdateAsync`/`AddAsync` — don't invent a different mechanism.

## Work tasks & dashboards (added 2026-09-28)
- **Work tasks** (`WorkTask` + join `UserWorkTask`) = a branch's recurring/fixed duties (e.g. warehouse: in/out/reports). Each belongs to one branch (name unique per branch), assigned to users **of that branch only** (`WorkTaskRules.EnsureAssigneesInBranchAsync`). `GetForUserAsync` filters by the user's *current* branch, so a transferred user's old tasks disappear. New assignees get a `WorkTaskAssigned` notification (RelatedEntityType `WorkTask` → UI `/tasks/:id`). Branch delete is guarded by `HasWorkTasksAsync`.

## Task board — assigned tasks (added 2026-09-28)
- **Two different "task" concepts — don't mix them:** `WorkTask` = a job function's fixed page (no statuses; the card opens a future page). `AssignedTask` = a task a leader sends down the hierarchy, tracked on a Kanban board (`Todo`/`InProgress`/`Done`).
- Hierarchy (Role-Permission, 2026-10-03): `AssignTaskToDepartment` → a **Department** of my branch, `AssignTaskToOffice` → an **Office** of my department, `AssignTaskToUser` → a **User** of my office. A role may hold several, so `CreateAssignedTaskRequestDto.TargetType` (`Department`/`Office`/`User`) is required when there is more than one; `Board` returns `targetTypes` + `hasScope`, and `Targets?type=` / `Targets?parentTaskId=` (delegation) list the options. A department task is handled by users of that department itself (no office) holding `HandleUnitTasks`, an office task by that office's `HandleUnitTasks` holders — `AssignedTaskRules.CanHandle`.
- Rules (`Application/Features/AssignedTasks/AssignedTaskRules.cs` is the single source): only the handler changes status (drag & drop); the creator edits (until Done) and deletes (only `Todo` with no subtasks); the handler can **delegate** (a child task with `ParentTaskId`, one level down), and the first delegation moves the parent `Todo→InProgress`. Viewing: SuperAdmin all, creator, handler, and holders of an assign/handle permission for tasks inside the unit that permission covers (`AssignedTaskRules.Scope`; the task stores `BranchId/DepartmentId/OfficeId` for this). Comments are for anyone who can view.
- History: `AssignedTaskActivity` (Created/StatusChanged/Comment/Delegated/Edited), cascades with the task. Notifications `TaskAssigned`/`TaskStatusChanged`/`TaskCommented`, `RelatedEntityType = "AssignedTask"` → UI `/task-board?task=ID` (use `router.navigateByUrl` for these links, since `navigate([...])` would encode the `?`).
- All FKs are Restrict → delete guards added to Department/Office/User delete handlers (`IAssignedTaskService.ExistsFor*`). Users tied to tasks must be deactivated, not deleted.
- API `api/AssignedTasks`: `Board?mode=incoming|outgoing|scope` (Done limited to the last 30 days), `Get/{id}`, `Targets`, `Create`, `Update/{id}`, `Status/{id}` `{status: 1|2|3}`, `Comment/{id}`, `Delete/{id}` — plain `[Authorize]`, all checks are in the rules. Migration `Add_AssignedTasks`.
- UI `features/task-board/`: `@angular/cdk` drag-drop (`cdkDropListGroup`; the enter predicate only accepts cards with `canChangeStatus`, and the update is optimistic with revert on error). The keyboard alternative is the status switch in `TaskDetailDrawer`. Forms are in `TaskFormDialog` (create/edit/delegate).

## Device inventory: Site → Device (added 2026-09-28; regions replaced by governorates 2026-10-03)
- Documentation/inventory feature owned by the **operations department of the technical branch** (replaces scattered Excel sheets). - Entities (`Domain/Entities`): `Site` (Name*, Description, Latitude*, Longitude*, `GovernorateCode`). **There is no `Region` entity/table any more** (user decision 2026-10-03, migration `Replace_Regions_With_Governorates`, which first appended each site's old region name to its description): the "region" of a site is one of the 14 fixed Syrian governorates, **derived by the server from the coordinates on every create/update** (`Features/Sites/GovernorateResolver` → `Application/Common/Governorates`, which embeds a copy of `public/maps/syria-governorates.geojson` — keep both files in sync; a point outside every governorate is rejected with an Arabic message). Don't re-add it.
- UI (`features/devices/`, routes guarded by `deviceGuard`). **In the sidebar since 2026-10-03** (user decision, replacing the old dashboard `DeviceShortcuts` frame, which was deleted): a "توثيق الأجهزة" section (التركيبات / المواقع / الأجهزة — صفحة المناطق حُذفت) shown to anyone holding any device permission (`DEVICE_ACCESS` in `core/constants/access.ts`, same group guards the `/devices` route): three pages — `devices/installations` (main page: governorate→site→device filters, search by IP/SN/user, password masked with show + copy for every viewer — user choice), `devices/sites` (location rendered as a Google Maps link when it's coordinates/URL), `devices/catalog`. Manage buttons only when `canManage`.
- **`Pass` is stored as plain text** (decided with the user 2026-09-28) — these are live device credentials needed for actual reversible use, not hashed like user passwords. Flagged here as the same category of tech debt as the hard-coded JWT key (#4 below); revisit if this ever needs to be more defensible (e.g. ASP.NET Data Protection API).
- Same IP twice at the same site is **allowed, only warned** in the UI (live warning under the IP field + ⚠ badge in the table) — user decision 2026-09-29; don't add a backend block.
- `Site.Name` is globally unique (like `Office.Name`); `Device.Name`/`SN` are not — multiple devices can plausibly share a name/model, so no uniqueness is enforced there.
- Delete guards (matching the Office/Department pattern): can't delete a `Site` with `DeviceSite` links (`HasDeviceLinksAsync`), can't delete a `Device` with `DeviceSite` links (`HasSiteLinksAsync`) — all throw a friendly `InvalidOperationException` instead of a raw FK-restrict 500.
- Endpoints, all under the four policies above (per operation, no per-entity split): `api/Sites`, `api/Devices`, `api/DeviceSites` (`GetAll` takes optional `?siteId=`/`?deviceId=`) — each with `Create`/`Update/{id}`/`Delete/{id}`/`Get/{id}`/`GetAll`, `[FromForm]` bodies, matching the Offices controller shape exactly.
