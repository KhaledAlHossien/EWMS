# EWMS — Employee Workflow Management System

Internal HR system: branches, departments, offices, users, roles/permissions, and a multi-stage **vacation request workflow**.

Org hierarchy: **Branch → Department → Office → User**. `Vacation` approval scoping deliberately stays at Department/Branch level only — it does NOT use Office (confirmed with the user 2026-09-27).
The old "Projects" feature was removed in commit `ba670e2` and replaced by Vacations.
Code comments and user-facing messages are in Arabic; keep that convention.

## Stack
- Backend: ASP.NET Core **.NET 10**, EF Core 10 + SQL Server (LocalDB, DB name `EWMS`), MediatR 12, FluentValidation 12, AutoMapper 16, JWT Bearer, BCrypt.
- Frontend: **Angular 22** standalone components. **Active UI is `F:\-EWMS-UI-main-main`** (separate folder, not a git repo; chosen by the user 2026-09-27). `EWMS.Client/` from older notes does not exist here.
- Solution file: `EWMS.slnx` (API, Application, Domain, Infrastructure). `EWMS/Class1.cs` is an empty leftover, not in the solution.

## Architecture (Clean Architecture + CQRS)
Dependencies: `API → Application, Infrastructure`; `Infrastructure → Application, Domain`; `Application → Domain`.

- **Domain/** — entities (`User`, `Branch`, `Department`, `Office`, `Role`, `Permission`, `RolePermission`, `Vacation`, `VacationType`, `UserToken`) and `Enums/VacationStatus`. `User.BranchId/DepartmentId/OfficeId` are **nullable and role-dependent** (see "User placement by role" below); `Office.DepartmentId` is required (belongs to exactly one department).
- **Application/**
  - `Features/<Feature>/Commands|Queries/<Action>/` → `XxxCommand` (IRequest), `XxxCommandHandler`, `XxxCommandValidator`.
  - `DTOs/Request`, `DTOs/Response`, `Helper/Profiles` (AutoMapper), `Interfaces/` (`IXxxService`).
  - `Common/Behaviors/ValidationBehavior` runs all FluentValidation validators in the MediatR pipeline.
  - Registered in `AddApplicationRegistrationServices.cs`.
- **Infrastructure/**
  - `Persistence/Data/DataContext.cs` (relationships, indexes, mostly `DeleteBehavior.Restrict`), `DbSeeder.cs`, `Migrations/`.
  - `Persistence/Repositories/*Service.cs` implement the Application interfaces (they are services/repositories over `DataContext`).
  - `AddInfrastructureRigstrationServices.cs` — DI + JWT config.
- **API/**
  - `SystemBuild/Program.cs` (entry; auto-runs migrations + seeding on startup), `AddAPIRigstrationServices.cs` (Swagger + authorization policies), `ApplicationPipeline.cs`.
  - `Controllers/` — thin, only call `_mediator.Send(...)`.
  - `Middlewares/ExceptionMiddleware.cs` maps exceptions → HTTP: `KeyNotFoundException`→404, `ArgumentException`/`InvalidOperationException`→400, `UnauthorizedAccessException`→401, `ValidationException`→400 with errors list. **Handlers signal errors by throwing these.**

Request flow: Controller → MediatR → ValidationBehavior → Handler → `IXxxService` → EF Core.

### Adding a new feature (follow existing pattern)
1. Entity in `Domain/Entities`, DbSet + config in `DataContext`, add migration (`dotnet ef migrations add <Name> -p Infrastructure -s API`).
2. Interface in `Application/Interfaces`, implementation in `Infrastructure/Persistence/Repositories`, register in Infrastructure DI.
3. DTOs + AutoMapper profile + Commands/Queries/Handlers/Validators under `Application/Features/<Feature>`.
4. Controller in `API/Controllers`; if a new permission is needed: add it to `Application/Common/AppPermissions.cs` only (one per operation: `ViewXs`/`CreateX`/`EditX`/`DeleteX`) — the policy and the DB row + SuperAdmin grant are generated from it.

## Auth & permissions
- `POST api/Auth/login` → JWT with claims: NameIdentifier (UserId), Email, Name, Role, `DepartmentId`, `BranchId`.
- Tokens are stored in `UserTokens`; `OnTokenValidated` rejects revoked/expired tokens, so logout really revokes.
- Current user: `ICurrentUserService` (also `IUserService.UserId`) reads claims.
- Authorization = named policies (`[Authorize(Policy = "CreateUser")]`) checked by `API/Authorization/PermissionAuthorizationHandler` against `RolePermissions` in the DB (per request — no re-login needed for enforcement, only for the UI's permission list).
- Seeded roles: `SuperAdmin`, `BranchManager`, `Manager`, `OfficeManager` (added 2026-09-28), `Emp`. Seeded admin user is in `DbSeeder.cs`.
- **Permissions are one per operation, everywhere** (user decision 2026-09-30; no `Manage…` permission exists any more). **Single source: `Application/Common/AppPermissions.cs`** (48 names + Arabic descriptions) — `DbSeeder` inserts missing ones, `AddAPIRigstrationServices` registers a same-named policy for each in a loop. Every policy used in a controller must be in that list and vice versa (checked: 48 = 48).
  - Users `ViewUsers`/`CreateUser`/`EditUser`/`DeleteUser` (`Auth/register` = `CreateUser`); Branches `ViewBranches`/`CreateBranch`/`EditBranch`/`DeleteBranch`; Departments `ViewDepartments`/`CreateDepartment`/`EditDepartment`/`DeleteDepartment`; Offices `ViewOffices`/`CreateOffice`/`EditOffice`/`DeleteOffice`; Roles `ViewRoles` (incl. `Roles/Permissions`)/`CreateRole`/`EditRole`/`DeleteRole`; Vacations `ViewVacations`/`CreateVacation`/`CancelVacation`/`ApproveVacation` (approve + `PendingForMe`); Vacation types `ViewVacationTypes`/`CreateVacationType`/`EditVacationType`/`DeleteVacationType`; Work tasks `ViewWorkTasks`/`CreateWorkTask`/`EditWorkTask`/`DeleteWorkTask`; Device inventory `ViewDevices`/`CreateDevice`/`EditDevice`/`DeleteDevice` (one set for regions+sites+devices+installations); Maintenance — see its section.
  - **Every read has a View permission too, including form lookups** (user decision 2026-09-30, reversing the first version where they were open): `ViewDepartments` (`Department/Get|GetAll`), `ViewVacationTypes` (`VacationTypes/Get|GetAll`), `ViewMaintenanceLookups` (the 4 maintenance lookup controllers). So a role needs the lookup View permission next to the create/edit permission that uses it: vacation form → `ViewVacationTypes`; maintenance request form/search → `ViewMaintenanceLookups`; any branch/department picker (incl. the UI `getBranchLookup()`) → `ViewDepartments`. Migration `Add_View_Permissions_For_Lookups` granted them to the roles that relied on those reads at the time (`ViewDepartments` → every role, `ViewVacationTypes` → roles with vacation permissions, `ViewMaintenanceLookups` → roles with maintenance-request/lookup permissions). View permission names are plural (`ViewXs`).
  - **Not permission-based (role + scope rules inside handlers), unchanged:** `AssignedTasks`, `Dashboard`, `Map`, `Notifications`, `WorkTasks/My|View`, `Auth/Me`, `Devices/MyAccess`.
  - The permission only opens the operation; record-level scoping still lives in the handlers/rules (`UserRules`, `OfficeRules`, vacation handlers, `MaintenanceRules`, department delete = own branch).
  - Privilege-escalation guard: a non-SuperAdmin can't grant a role holding `CreateBranch`/`EditBranch`/`DeleteBranch` (`AppPermissions.IsBranchManagement`, used by role create/update, `UserRules`, `AuthService.RegisterAsync`).
- **Role grants:** SuperAdmin gets **every** permission on each startup (`DbSeeder`). The other seeded roles get defaults **only when the role row is first created** (fresh DB: vacation permissions + `ViewDepartments` + `ViewVacationTypes`) — after that the seeder never touches them, so the user's edits from the Roles page stick (user decision 2026-09-30: "I'll adjust the other roles myself"). Don't reintroduce per-startup grants for non-SuperAdmin roles.
- Renaming/removing a permission needs a migration (the seeder only adds): insert new rows, copy each role's grants old→new, delete the old rows (cascade). See `Split_Maintenance_Permissions` and `Split_All_Permissions` (the latter also dropped `ManageVacations`, which never guarded any endpoint, and the dead "Project" policies were removed from the API).
- **UI follows the split (updated 2026-09-30):** `core/constants/access.ts` mirrors `AppPermissions.cs` (keep them in sync). Admin pages open with the View permission and show each button by its own permission (`canCreate`/`canEdit`/`canDelete`; inline-form pages use `can().create|edit|delete`). Exception: pages that manage lists everyone can read — departments, vacation types, maintenance lookups — appear in the sidebar/routes only for holders of Create/Edit/Delete (`MANAGE_DEPARTMENTS`, `MANAGE_VACATION_TYPES`, `MANAGE_MAINTENANCE_LOOKUPS` + `data.anyPermission` in `permissionGuard`), because the View permission alone is granted to every role that needs the dropdown. Device pages use `MyAccess.canCreate/canEdit/canDelete`. Users must re-login after the migration to get the new permission list.

## Vacation business rules (core domain) — reviewed & hardened 2026-09-27
- Status flow: `PendingManager (1)` → `PendingBranchManager (3)` → `Approved (4)`; any stage can → `Rejected (5)` (stores RejectedByUserId, reason, date).
  `PendingAdministrative` was removed entirely 2026-09-27 (enum member, translations, `GetPendingForAdministrativeAsync`, and the status conditions in `VacationService`'s day-count/overlap queries). Its old int value (`2`) is left unassigned/reserved in the enum comment — never reuse it.
  A `Cancelled (6)` status was added the same day: the vacation's owner can cancel it (soft — `Status = Cancelled`, record kept for audit) only while it's `PendingManager` or `PendingBranchManager`; blocked once `Approved`/`Rejected`/already `Cancelled`. Endpoint: `PUT api/Vacations/Cancel/{id}`, policy `CancelVacation`. `Cancelled` is intentionally excluded from `HasOverlappingVacationAsync` and the paid/unpaid day-count queries — cancelling frees up that period and doesn't count against the monthly quota.
- Approver checks (`ApproveVacationCommandHandler`): role `Manager` in same department for stage 1; role `BranchManager` in same branch for stage 2; `SuperAdmin` bypasses both. Role checks are by role **name**. Self-approval is blocked (`vacation.UserId == currentUser.Id` → Unauthorized) for everyone except SuperAdmin.
- Create (`CreateVacationCommandHandler`): **BranchManager and SuperAdmin cannot submit vacations** (no department → `InvalidOperationException`; UI hides the form). A **Manager's own vacation skips stage 1** and starts at `PendingBranchManager` (so it's never stuck needing another Manager). End ≥ start, no overlap with pending/approved vacations, `VacDayCount = days inclusive`, Department/Branch copied from the user. **Returns `List<VacationResponseDto>`, not a single one** — see paid-day splitting below.
- Paid rule (day-level splitting, confirmed with user 2026-09-27): if `VacationType.IsPaid == false` → whole request unpaid. Otherwise max **2 paid days per month, pooled across all IsPaid=true types** (regular paid + sick + overtime-reward share the same monthly cap). If a single request would cross the cap mid-range, `BuildPaidUnpaidSegmentsAsync` walks day-by-day and **splits it into separate `Vacation` rows** — one covering the still-available paid days, another (or more, if it spans several months) covering the rest as unpaid. Each resulting row goes through the normal independent approval workflow.
- Visibility/scoping (this was broken before the review — controller had zero policies applied despite policies existing, and `Emp` role had **no vacation permissions at all** in `DbSeeder`, silently masked by that same gap):
  - `Emp` role now seeded with `ViewVacations` + `CreateVacation`. **Anyone with an old JWT needs to re-login** to pick up new permissions (they're baked into the token at login).
  - `GetAll` is now role-aware ("vacations relevant to me"): SuperAdmin → everything, BranchManager → own branch (`GetByBranchIdAsync`), Manager → own department (`GetByDepartmentIdAsync`), anyone else → own only. This is how "رئيس القسم يرى إجازات قسمه" / "رئيس الفرع يرى إجازات فرعه" is satisfied for *all* statuses, not just pending ones (`PendingForMe` only ever showed pending).
  - `GetById`/`User/{userId}` now check ownership/scope inside the handler (owner, or the dept Manager, or the branch BranchManager, or SuperAdmin) — previously any authenticated user could view anyone's vacation by id/userId.
- Endpoints (`api/Vacations`, all now behind proper policies): `Create` (form, policy `CreateVacation`), `Cancel/{id}` (PUT, policy `CancelVacation`, owner-only), `Approve/{id}` (PUT body `{approve, reason}`, policy `ApproveVacation`), `PendingForMe` (policy `ApproveVacation`), `Get/{id}` / `GetAll` / `User/{userId}` / `My` (policy `ViewVacations`, scoped per role as above).

## Offices (added 2026-09-27)

Scoping (`Offices/OfficeRules`): a user with a department (Manager) manages only their department's offices; a user without one (BranchManager) manages offices of every department in their branch; SuperAdmin everything.

  SuperAdmin → no branch/department/office; BranchManager → branch only; Manager → branch + department (no office); Emp and any custom role → branch + department + office.

Migration `Make_User_Placement_Optional` made the columns nullable and NULLed existing data to match. JWT `DepartmentId`/`BranchId` claims are empty (→ 0 in `ICurrentUserService`) when absent; users must re-login after their placement changes.

- Deleting a Department/Office that still has children throws a friendly `InvalidOperationException` (`HasOfficesAsync` / `HasUsersAsync` checks) rather than letting the DB FK-restrict raise a raw 500 — **always add this guard for any new parent→child relationship**, it's easy to forget.

Any future required-FK-on-populated-table migration should follow this same backfill pattern.

## Notifications (added 2026-09-27)
- New `Domain.Entities.Notification` (recipient `UserId`, `Title`, `Message`, `Type` enum, optional `RelatedEntityType`/`RelatedEntityId` for deep-linking, `IsRead`/`ReadAt`). Cascade-deletes with its recipient `User`.
- **Real-time push via SignalR (added 2026-09-27).** Hub `API/Hubs/NotificationHub` at `/hubs/notifications` (`[Authorize]`, server→client only, method name `notification`, payload `NotificationResponseDto`). Routing is `Clients.User(UserId)` via the default NameIdentifier user-id provider.
  - Push is automatic: Infrastructure `NotificationService.AddAsync/AddRangeAsync` call `INotificationPusher` (Application interface, implemented by `API/Hubs/SignalRNotificationPusher`, registered in `AddAPIRigstrationServices`) **after** SaveChanges. Push failures are logged and swallowed — the DB row is the source of truth. So any new notifier gets real-time for free; don't call the hub directly.
  - JWT over websocket: `OnMessageReceived` accepts `?access_token=` **only** for `/hubs/*`, and `OnTokenValidated` falls back to that query token so the revoked-token check still applies. An already-open socket is not killed on logout; the client stops it itself.
  - UI: `NotificationService.start()` (SignalR + auto-reconnect, 60s fallback poll of `UnreadCount`), toast popups (`features/layout/notification-toasts.ts`), browser desktop `Notification` when the tab is hidden (opt-in button on the notifications page). `proxy.conf.json` has a `/hubs` entry with `ws: true` — changing it requires restarting `ng serve`.
- `Application/Features/Vacations/VacationNotifier.cs` is a static dispatch helper (same pattern as `UserRules`) called from `CreateVacationCommandHandler`, `ApproveVacationCommandHandler`, and `CancelVacationCommandHandler`. It resolves recipients by role+department/branch via the existing `IUserService.GetByDepartmentAsync`/`GetByBranchAsync` (filtered client-side to `Role.Name == "Manager"`/`"BranchManager"`) — no new user-lookup repo methods were needed.
- Full trigger map (verified live end-to-end): submit → dept Manager(s); Manager approves → employee + branch Manager(s) (forwarded); Manager rejects → employee only (branch never sees it); BranchManager approves (final) → employee + dept Manager(s); BranchManager rejects (final) → employee + dept Manager(s); employee cancels → dept Manager(s) always, **plus** branch Manager(s) too if it had already reached `PendingBranchManager`.
- A `CreateVacationCommand` that splits into paid+unpaid segments (see above) fires one `VacationSubmitted` notification per segment/entity created.
- Endpoints (`api/Notifications`, plain `[Authorize]`, every action implicitly scoped to the caller): `GET My?unreadOnly=`, `GET UnreadCount`, `PUT MarkAsRead/{id}` (403/401 if not the owner), `PUT MarkAllAsRead`.
- If you add a new workflow with async multi-party approval later, follow this same shape: a `Notification` row per recipient, a static `<Feature>Notifier` helper, called from inside the command handler right after `UpdateAsync`/`AddAsync` — don't invent a different mechanism.

## Task board — assigned tasks (added 2026-09-28)
- **Two different "task" concepts — don't mix them:** `WorkTask` = a job function's fixed page (no statuses; the card opens a future page). `AssignedTask` = a task a leader sends down the hierarchy, tracked on a Kanban board (`Todo`/`InProgress`/`Done`).
- Hierarchy (user decision): BranchManager → **Department** of his branch, Manager → **Office** of his department, OfficeManager → **User** in his office (the last hop was added as the natural extension). SuperAdmin only views. The target type comes from the creator's **role**, so the client only sends `TargetId`. A department task is executed by that department's `Manager`s, and an office task by its `OfficeManager` — "handler" in `AssignedTaskRules.CanHandle`.
- Rules (`Application/Features/AssignedTasks/AssignedTaskRules.cs` is the single source): only the handler changes status (drag & drop); the creator edits (until Done) and deletes (only `Todo` with no subtasks); the handler can **delegate** (a child task with `ParentTaskId`, one level down), and the first delegation moves the parent `Todo→InProgress`. Viewing: SuperAdmin all, leaders their scope (the task stores `BranchId/DepartmentId/OfficeId` for this), creator, and handler. Comments are for anyone who can view.
- History: `AssignedTaskActivity` (Created/StatusChanged/Comment/Delegated/Edited), cascades with the task. Notifications `TaskAssigned`/`TaskStatusChanged`/`TaskCommented`, `RelatedEntityType = "AssignedTask"` → UI `/task-board?task=ID` (use `router.navigateByUrl` for these links, since `navigate([...])` would encode the `?`).
- All FKs are Restrict → delete guards added to Department/Office/User delete handlers (`IAssignedTaskService.ExistsFor*`). Users tied to tasks must be deactivated, not deleted.

## Device inventory: Region → Site → Device (added 2026-09-28)
- Documentation/inventory feature owned by the **operations department of the technical branch** (replaces scattered Excel sheets). The entities have no FK to the org hierarchy, but **access is department-based** (user decision 2026-09-28, UI built the same day): `ViewDevices` / `CreateDevice` / `EditDevice` / `DeleteDevice` policies use `DeviceAccessRequirement(DeviceOperation)` → `IDeviceAccessService` (Infrastructure `DeviceAccessService`). **View** = anyone in the owner department (`appsettings.json` → `DeviceInventory:OwnerDepartmentId`, currently `1` = العمليات) **or** a role with `ViewDevices`. **Create/Edit/Delete** = that department's `Manager` (all three) **or** a role with the matching `CreateDevice`/`EditDevice`/`DeleteDevice` (SuperAdmin by default). Department comes from the JWT claim, so users re-login after a placement change. `GET api/Devices/MyAccess` returns `{canView, canCreate, canEdit, canDelete, canManage, inOwnerDepartment}` for the UI (`canManage` = any of create/edit/delete) — keep the policy and this endpoint on the same service so they never disagree.
- Entities (`Domain/Entities`): `Region` (Name*, Description, Latitude*, Longitude*) 1→N `Site` (Name*, Description, Latitude*, Longitude*, RegionId*). Coordinates are nullable in the DB (legacy rows) but required by the validators, inside Syria's bounds (`Application/Common/GeoRules`). The old free-text `Site.Location` was dropped by migration `Add_Map_Coordinates_InstallLocation`, which first parsed "lat, lng" text into the new columns and appended any other text to `Description`. `Device` (Name*, Model, Description) is a standalone **type/model**; `DeviceSite` is the many-to-many join table between `Device` and `Site` (a device can be installed at multiple sites, a site can host multiple devices) and carries the per-installation info: `SN` (serial number of the physical unit — moved off `Device` by migration `Move_SN_To_Installation`, which copied each device's SN to its installations and kept orphan SNs in the device description), `InstallLocation` (precise spot inside the site, e.g. "عند البوابة الرئيسية"), `Ip*`, `SubnetMask*` (both validated as IPv4 in the command validators), `UserName*`, `Pass*`, `Note`. **`Device` is a reusable type/model, not a physical unit** (user correction 2026-09-29): the same device can be installed several times at the same site with different IP/credentials — there is **no** uniqueness on `(DeviceId, SiteId)` (dropped by migration `Allow_Repeated_Device_Per_Site`, and the `ExistsLinkAsync` handler checks were removed). Don't re-add it.
- UI (`features/devices/`, routes guarded by `deviceGuard`). **Not in the sidebar** (user decision 2026-09-28): the entry point is the framed `DeviceShortcuts` section ("توثيق الأجهزة", 4 cards with counts) placed on the operations head's own department dashboard and the employee / office-head dashboards — it renders only when `canView && inOwnerDepartment` (`MyAccess` returns `inOwnerDepartment`), so **not** on the SuperAdmin overview (user decision) nor for other departments even if granted `ViewDevices`. SuperAdmin still has API/page access by URL.: four separate pages (user choice) — `devices/installations` (main page: region→site→device filters, search by IP/SN/user, password masked with show + copy for every viewer — user choice), `devices/regions`, `devices/sites` (location rendered as a Google Maps link when it's coordinates/URL), `devices/catalog`. Manage buttons only when `canManage`.
- **`Pass` is stored as plain text** (decided with the user 2026-09-28) — these are live device credentials needed for actual reversible use, not hashed like user passwords. Flagged here as the same category of tech debt as the hard-coded JWT key (#4 below); revisit if this ever needs to be more defensible (e.g. ASP.NET Data Protection API).
- Same IP twice at the same site is **allowed, only warned** in the UI (live warning under the IP field + ⚠ badge in the table) — user decision 2026-09-29; don't add a backend block.
- `Region.Name` and `Site.Name` are globally unique (like `Office.Name`); `Device.Name`/`SN` are not — multiple devices can plausibly share a name/model, so no uniqueness is enforced there.
- Delete guards (matching the Office/Department pattern): can't delete a `Region` with `Site`s (`HasSitesAsync`), can't delete a `Site` with `DeviceSite` links (`HasDeviceLinksAsync`), can't delete a `Device` with `DeviceSite` links (`HasSiteLinksAsync`) — all throw a friendly `InvalidOperationException` instead of a raw FK-restrict 500.
- Endpoints, all under the four policies above (per operation, no per-entity split): `api/Regions`, `api/Sites` (`GetAll` takes optional `?regionId=`), `api/Devices`, `api/DeviceSites` (`GetAll` takes optional `?siteId=`/`?deviceId=`) — each with `Create`/`Update/{id}`/`Delete/{id}`/`Get/{id}`/`GetAll`, `[FromForm]` bodies, matching the Offices controller shape exactly.
- Migration `Add_DeviceInventory` creates all four tables in one migration (no existing data to backfill, unlike `Add_User_OfficeId`).

## Maintenance: requests & tasks (added 2026-09-29)
- Entities in `Domain/Entities/Maintenance/` (namespace `Domain.Entities.Maintenance`): `MaintenanceRequest` (a device brought in for repair: client name/phone, `DeviceType`, `DamageType`, `DeviceCompany`, model, serial number, accessories, description, `MaintenanceRequestStatus`), `MaintenanceTask` (a job an employee worked on: location, requesting party, required work, completed works), and 4 lookup tables (`DeviceType`, `DeviceCompany`, `DamageType`, `MaintenanceRequestStatus` with a `#RRGGBB` `Color`). Unrelated to the `Device`/`DeviceSite` inventory — don't merge them.
- **Owner** (`UserId`) = whoever creates the record; for a request that person is also the technician (user decision). Set from the current user and never editable. `DepartmentId` is a snapshot of the owner's department at creation (like `Vacation`), so the head of that department keeps seeing it after a transfer. `StartedAt`/`CompletedAt` are entered manually (optional, completed ≥ started); `CreatedAt`/`UpdatedAt` are automatic.
- **Scope** (`Application/Features/Maintenance/MaintenanceRules.cs`, single source): a record is visible/editable/deletable by its owner, the `Manager` of the same department, and SuperAdmin. The policy decides *which operation*, the rules decide *which records*.
- **Permissions — one per operation** (user decision 2026-09-29): tasks `ViewMaintenanceTasks`/`CreateMaintenanceTask`/`EditMaintenanceTask`/`DeleteMaintenanceTask`; requests `ViewMaintenanceRequests` (view + search + technicians)/`CreateMaintenanceRequest`/`EditMaintenanceRequest`/`DeleteMaintenanceRequest`; the 4 lookup tables share `ViewMaintenanceLookups`/`CreateMaintenanceLookup`/`EditMaintenanceLookup`/`DeleteMaintenanceLookup` (the View one was added 2026-09-30 — anyone filling or searching requests needs it for the dropdowns). Policies are registered in a loop in `AddAPIRigstrationServices.cs`. Only SuperAdmin has them by default — grant them to roles from the Roles page. The first version had grouped permissions (`ManageMaintenanceTasks`, `ManageMaintenanceLookups`, Edit = edit+delete); migration `Split_Maintenance_Permissions` inserts the new ones, copies every existing grant to its per-operation equivalents, and deletes the old ones — follow that pattern for future permission renames (the seeder only adds). 5 default statuses are seeded once (only if the table is empty).
- **Search** `GET api/MaintenanceRequests/GetAll` (paged `PagedResultDto<T>`, pageSize ≤ 100, newest first), filters AND-combined: `serialNumber`/`model` = **starts with** (`LIKE 'x%'` → index seek on `IX_..._SerialNumber`/`_Model`), `clientName` = **contains** (scans the narrow name index), and exact `deviceCompanyId`/`technicianId`/`deviceTypeId`/`damageTypeId`/`statusId` (composite `(FK, CreatedAt)` indexes). Don't switch serial/model to `Contains` — it drops the seek. If "contains" on large volumes gets slow, the next step is SQL Server Full-Text Search (not available on LocalDB). `GET api/MaintenanceRequests/Technicians` feeds the technician filter.
- Layout follows the compact AssignedTasks style: one file per lookup (`Features/Maintenance/<Lookup>/<Lookup>Feature.cs` = records + validators + one handler), `Requests/MaintenanceRequestCommands.cs` + `...Queries.cs`, `Tasks/MaintenanceTaskFeature.cs`; DTOs in `DTOs/Request/MaintenanceRequestDtos.cs` / `DTOs/Response/MaintenanceResponseDtos.cs`; one `MaintenanceProfile`; JSON (`[FromBody]`) bodies. Controllers: `api/DeviceTypes`, `api/DeviceCompanies`, `api/DamageTypes`, `api/MaintenanceRequestStatuses`, `api/MaintenanceRequests`, `api/MaintenanceTasks`.
- All FKs Restrict → delete guards: lookups in use can't be deleted; User and Department delete handlers check `IMaintenanceRequestService`/`IMaintenanceTaskService.ExistsFor*`. Migration `Add_Maintenance`.
